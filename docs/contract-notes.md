# 実装メモ: 操作契約・データ契約に記述がなく、実装側で補った解釈

共通コマンド処理(`src/control/`、Issue #18)の実装で、契約(`specifications/synthesizer/operation-contract.md`、`data-contract.md`)が曖昧・不足・矛盾していた点と、採った解釈の一覧。契約への追記の候補であり、契約の正本ではない。契約の受入例・無効例の期待値は、契約の表のまま使っている。

## 契約内の矛盾
| 箇所 | 内容 | 採った解釈 |
|---|---|---|
| 操作契約 CMD-25 と EVT-03 | 人が現在と同じ音量を設定して上限だけが変わる場合、CMD-25 は「通知は出さない」、EVT-03 の表は「エージェント上限が変わったとき出る」 | CMD-25 に従い、通知は出さない |
| 操作契約 §3.3 と各コマンドのエラーの列挙順 | §3.3 は「対象の存在 → 値と規則」の順。CMD-02 は ERR-103, 106, 121、CMD-06 は ERR-114, 116, 106 の順 | 引数の形(ERR-003)を最初にし、その後は各コマンドの列挙順。module.add: 003 → 101 → 105 → 103 → 106 → 121 → 122/123。cable.connect: 003 → 両端の 102/111 → 112 → 113 → 114 → 116 → 106 |

## 操作契約の不足
| 箇所 | 採った解釈 |
|---|---|
| §3.1 封筒の未知のフィールド | args の未知キーしか規定がない。封筒の未知キー(`actor` を含む)は ERR-001 で拒否(打ち間違いの `expected_revision` を黙って無視しないため) |
| §5 ERR-003「IDの書式」 | 書式を検査するのは新しく付けるIDだけ。既存の対象を指すIDは、存在しなければ ERR-102 / ERR-115 |
| §2.2 次番号と失敗 | 失敗した要求(batch の途中失敗を含む)が使った番号は消費しない |
| CMD-09 batch | `ops` が空なら ERR-003、500 超なら ERR-106、未定義のコマンド名は ERR-132、要素の余分なキーは ERR-003。`args` の省略は `{}` |
| CMD-05 module.move | `ui` は x・y が必須で、他のキーは保持する。既存の `ui` に上書きでマージする |
| CMD-11 patch.new | 既に空のパッチでも変更として扱う(リビジョン +1、履歴1件) |
| §9.4 履歴のまとめ | 「同じ操作者」は種別と client_id の両方が一致。undo/redo を挟んだらまとめを切る |
| §7 冪等キー | 鍵は操作者をまたいで1つの集まり。再送の応答は `request_id` と `replayed` だけ差し替える |
| §14 seed | `duplicate_seed` の `details` は `{module_id, param, value, conflicts}`。ノイズ源と S&H は同じ集まりで数える |
| CMD-21 | `stopped` のとき `fs`・`engine_revision` は null、計数は 0 |
| CMD-01 module.list_types | 契約が求める `category`、ポートの `unit` と `unconnected`、パラメータの enum の区別と `values` は、実装の定義にまだなく `null` で返す。真偽型(`bool`)は区別する |
| 未対応のコマンド | patch.save / load / list / read / delete は、ファイル保存が未実装のため ERR-207(`details.reason: "not_implemented"`)。手前の検査(権限、引数の形、パッチ名)は実装済み |

## データ契約の不足
| 箇所 | 採った解釈 |

| §8 DAT-V07 移行の道がない古い仕様版(例 `"0.0"`) | 文面では通るが、拒否する(ERR-205) |

## Issue #20 で追加した解釈(保存のコマンド、ローカルサーバー)
### 保存のコマンド(`src/control/controller.ts`)
| 箇所 | 採った解釈 |
|---|---|
| CMD-12 patch.save のエラー順 | 列挙順どおり 003 → 201 → 203 → 005 → 106 → 206 → 207 |
| ERR-106 / ERR-207 の `details` | 値の名前が契約にない。ERR-106 は `limit: "patch_files"`、ERR-207 は保存先の失敗種別と `operation`(read / write / list / remove) |
| DAT-36「書式が不正な saved_by」 | オブジェクトでない、余分なキーがある、`client_id` が文字列でない、のいずれかを人の保存として扱う |

### ローカルサーバー(`src/server/app.ts`)
| 箇所 | 採った解釈 |
|---|---|
| §3.3 の検査順と認証 | HTTP は契約どおり ERR-011 → ERR-001 → ERR-012 → ERR-004(未認証でも本文を上限まで読む)。WebSocket は接続時に認証する。Host の検査は契約にない輸送層の検査として最初に行う |
| HTTP の状態コード(契約になし) | ERR-001/012 は 400、ERR-004 は 401(Origin・Host が原因なら 403)、ERR-011 は 413、ERR-006 は 503、ERR-007 は 504。それ以外は `ok:false` でも 200 |
| サーバーが作る応答の `revision` など | タブがあり認証済みなら、タブの応答・通知から覚えた最後の値。未認証・タブなしでは null |
| 応答待ち中にタブが切れた | 待たずに ERR-007(`details.reason: "tab_disconnected"`)。適用されたか不明という意味 |
| 要求の大きさと WebSocket | ERR-011 を返せるよう、受信上限は要求上限の2倍。それを超える1通は接続を閉じる |
| タブなしのとき | ERR-002 → ERR-005 → ERR-006 の順(引数の検査より先に ERR-006)。直接答える3コマンド(patch.list、patch.read、module.list_types)では `expected_revision` を比べない |
| 2つ目のタブ | `hello { accepted: false, reason: "another_tab" }` を送って閉じる。1つ目が閉じれば次の接続を受け付ける |
| エージェント用の口の Origin | 自サーバーのオリジンでも拒否。CORS の許可ヘッダは出さない |
| 保存フォルダ | シンボリックリンクや同名フォルダは読出しを失敗にする。書き込みは一時ファイルに書いてから名前を付ける |

### 認証境界についての注意(判断材料)
- タブ用トークンは配信する index.html に埋めている。同じマシンの**ブラウザ以外のプロセス**は `GET /` でそれを読め、Origin を偽ってタブとして接続できる。そうすると、保存先を直接操作でき、エージェントの要求を受け取る側にもなれる。
- 契約は、上書きの制限(§15.3)を「認証境界ではなく誤操作への歯止め」としている。同じ利用者の権限で動くプロセスは、保存フォルダを直接読み書きできるので、これ自体は新しい権限を与えない。ただし、タブになりすませる点は記録しておく(判断記録 OPEN-016)。
- 上書きの権限(誰の操作か)はタブ側で検査している。サーバーの保存操作は操作者を知らない。

### 仮の値
- 保存フォルダの既定の場所: 環境変数 `SYNTH_PATCH_DIR`、なければ `~/.agent-modular-synth/patches`。
- 待受ポート 47800、応答待ち 5 秒、要求の上限 2 MiB、保存パッチ 1000 件。

### 実装の重複(整理が残る)
- サーバーがタブなしで直接答える `module.list_types`・`patch.list`・`patch.read` と、封筒の検査は、Session / Controller と同じ規則を `src/server/app.ts` に複製している(一致は試験で確認)。共有の関数にまとめるのが望ましい。

## Issue #22 で追加した解釈(MCP アダプタ、編集画面)
### MCP アダプタ(`src/mcp/`)
| 箇所 | 採った解釈 |
|---|---|
| アダプタ自身の失敗の形(サーバーに届かない、トークンがない等。契約 §17 に記述なし) | 契約の失敗応答と同じ形で、`error.id: null`、`error.code` は `adapter_no_token` / `adapter_server_unreachable` / `adapter_bad_response`、`details.applied` は `"no"` / `"unknown"`。新しい `ERR-…` は作っていない |
| 存在しないツール名(人のみのコマンドを含む) | MCP のプロトコルエラー。サーバーへは何も送らない |
| 出力 | テキスト1つ(応答の封筒の JSON)。`ok: false` は isError で返し、`error` を保つ |
| `client_id` | 固定の `mcp`(環境変数 `SYNTH_CLIENT_ID` で変更可) |
| 入力スキーマ | 「どちらか一方」「少なくとも一方」の条件は、スキーマではなく説明文に書く。入力の検査はアダプタでせず、サーバーの契約のエラーをそのまま返す |
| 接続先 | `http://127.0.0.1[:port]` か `http://localhost[:port]` だけ。それ以外は起動しない。リダイレクトにも従わない |
| サーバー停止・トークンなし | 起動は失敗させず、ツールの呼出し時にエラー結果を返す |

### トークンファイル(設計判断)
- サーバーは起動時にエージェント用トークンをファイル(既定 `~/.agent-modular-synth/agent-token`、環境変数 `SYNTH_TOKEN_FILE`)へ書く。権限は本人だけが読める 0600。終了時に、自分が書いた内容のままのときだけ消す。強制終了では残る(次の起動で上書き)。
- アダプタは、環境変数 `SYNTH_AGENT_TOKEN` があればそれを使い、なければファイルを呼出しのたびに読む。
- 同じ利用者の権限で動くプログラムを信頼する方針(DEC-014)と同じ考え方。サーバーを2つ動かすと、後から起動した方のトークンが入る。
