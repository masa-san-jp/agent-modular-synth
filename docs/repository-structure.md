# リポジトリ構成案

状態：**提案**  
記録日：2026-11-12

## 目的と位置付け

モジュラーシンセの調査から設計へ進むための、成果物の格納先と責務の案です。これは実装済みの構成を示すものでも、技術スタックを確定するものでもありません。

「公開資料で確認したリファレンス情報」「そこから抽象化した機能別仕様」「本製品の採用判断・全体仕様」を分離し、根拠を相互リンクで追跡できるようにします。

## 提案するディレクトリ構成

```text
agent-modular-synth/
├── README.md
├── references/
│   ├── instruments/
│   ├── modules/
│   ├── sources/
│   └── index.md
├── specifications/
│   ├── modules/
│   └── synthesizer/
└── plans/
```

この構成案自体は `docs/repository-structure.md`（本ファイル）に記録します。上のツリーは調査・仕様・計画の成果物の配置案です。内容ができた時点で必要なファイルとディレクトリを作り、空の階層やプレースホルダーを埋めることは目的にしません。

## 各格納先の役割

| 格納先 | 役割 | 対応する作業 |
| --- | --- | --- |
| `README.md` | プロジェクトの入口。目的と各正本・Issueへの導線。仕様本文を重複掲載しない。 | 全段階 |
| `references/instruments/` | 実機・ソフトウェアの機種単位の調査記録。モジュラー／セミモジュラー等の区別、版、特徴、構成・制約を記録する。 | #1 |
| `references/modules/` | 既存製品の個別モジュールの調査記録。ポート、パラメータ、公開された挙動、制約を出典付きで記録する。 | #1 |
| `references/sources/` | 出典一覧・台帳。原文URL、資料名・版、節／ページ、確認日、実際に確認した範囲、未確認を記録する。 | #1 |
| `references/index.md` | 調査DBの検索・分類・比較の入口。機種・モジュール・出典を参照する。 | #1 |
| `specifications/modules/` | 製品名に依存しない機能別仕様。入出力、状態更新、信号・時間の条件、制約、再現・検証例を定める。 | #2 |
| `specifications/synthesizer/` | オリジナルシンセ全体の仕様。採用機能、構成、動作環境、人とエージェントの操作契約、保存・互換性・検証方針を定める。 | #3 |
| `plans/` | 実装計画、依存関係、未決事項とその判断・決定方法。仕様の代替正本にしない。 | #3 |

## 混同しない境界

- `references/` は一次情報等で**確認した事実と確認範囲**の正本。公開資料そのものの無断転載置場ではありません。資料の主張、第三者評価、実測、未確認を区別します。
- `specifications/modules/` は**抽象化した機能の振る舞い**の正本。原機の記録と、こちらの抽象化・設計上の仮定を区別します。
- `specifications/synthesizer/` は**本製品に採用する設計**の正本。調査した機能をすべて採用するとは限りません。
- `plans/` は**仕様をどう実現するか**と未決事項を扱います。仕様変更が必要なら仕様側を更新し、計画だけで仕様を上書きしません。
- `references/modules/` は既存機種のモジュール、`specifications/modules/` は抽象化した機能仕様です。同名の末尾ディレクトリでも役割が異なります。

## ID・相互リンクの方針

1. 調査レコード、出典、機能仕様、製品要求を識別できるID規則を各作業で定めます。データ形式・具体的な採番形式は本案では固定しません。
2. 機種・個別モジュールの調査記録から、出典IDと該当箇所へ辿れるようにします。
3. 機能仕様から、抽象化の根拠となったリファレンスID・出典へリンクします。
4. 製品仕様から、採用する機能仕様と採用理由へリンクします。採用しない機能や未決事項も区別します。
5. 実装計画は製品仕様・機能仕様のIDを参照し、仕様本文をコピーしません。
6. READMEと索引から正本へ到達できるようにします。同一リポジトリ内は相対リンクを基本とし、存在しない将来ファイルはリンクせず予定のパスとして記載します。
7. パスやIDを変更する際は参照元も更新し、重複ID・参照切れを検査します。出典の版や確認履歴を保持します。

## Issueとの対応

- [#1 リファレンス調査・出典付きDB](https://github.com/masa-san-jp/agent-modular-synth/issues/1) → `references/`
- [#2 再現可能な機能別モジュール仕様](https://github.com/masa-san-jp/agent-modular-synth/issues/2) → `specifications/modules/`
- [#3 製品仕様・操作契約・実装計画](https://github.com/masa-san-jp/agent-modular-synth/issues/3) → `specifications/synthesizer/` と `plans/`

順序は **#1 → #2 → #3**。各Issueの完了要件に従い、成果物の場所と検査結果を報告します。本案の記録自体は、調査DBや仕様が完成したことを意味しません。

## 実装用の構成は未定

ソースコード、音声処理、UI、エージェント接続、テスト、ビルド・配布等のディレクトリは、製品設計後に決めます。ここでは特定の言語、フレームワーク、MCP、デスクトップ方式、DB製品を確定せず、実装用の空ディレクトリも作成しません。
