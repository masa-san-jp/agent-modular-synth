# エンジンの高速化(音声ファイルの書き出しの速度)

2026-11-24。作業用のクラウドのコンテナ(共用。Intel Xeon 2.10 GHz、4 コア)、Node.js v22。数値は同じ機械・同じ時間帯で、変更の前後を測ったもの。共用の機械なので、数 % の揺れがある。

## 1. 結論
- 音声ファイルの書き出し(41 モジュールのテクノ、80.2 秒)が **62.6 秒 → 37.4 秒**(実時間の 1.28 倍 → 2.14 倍の速さ)。
- **出力は 1 バイトも変わっていない**(書き出した WAV の MD5 が、変更の前後で同じ)。検証例 288 件、単体試験もすべて合格。
- 実時間の演奏も同じエンジンなので、軽くなった。単独計算の負荷(1.0 が実時間の限界)は、54 モジュールで 0.62 → 0.40、108 モジュールで 1.25 → 0.79(**108 モジュールが実時間に収まるようになった**)。

## 2. 何を変えたか(すべて、計算の結果を変えない変更)
| 変更 | 内容 |
|---|---|
| つながっていない出力を写さない | エンジンは 1 サンプルごとに、全モジュールの全出力を「次のステップ用の控え」に写していた。ケーブルがつながっていない出力の控えは誰も読まないので、写すのをやめた。後からケーブルをつないだとき・スナップショットを取るときに、出力から写し直す(出力は最後の値を持ち続けているので、毎回写した場合と同じ値になる) |
| 入力の写しを 1 本の表に | ケーブル 1 本ごとの「どこからどこへ写すか」を、手順を作るときに 1 本の表にしておく。単音(チャンネル 1 つ)は、繰り返しを使わずに 1 個だけ写す |
| パラメータの読み出し | 名前から値を引く表を、Map からふつうのオブジェクトに替えた |
| 発振器・フィルタの係数 | 音程やカットオフが前のサンプルと同じなら、べき乗や tan を計算し直さず、前の結果を使う |
| MIDI-CV | メッセージのないサンプルで配列を作り直さない。使わない声の出力を、毎サンプル 0 で書き直さない |

## 3. 測定
### 3.1 音声ファイルの書き出し(`npm run render`。41 モジュール、楽譜 5 個、80.2 秒)
| 段階 | 所要 | 実時間の何倍の速さ |
|---|---|---|
| 変更前 | 62.6 秒 | 1.28 |
| パラメータの読み出し、発振器・フィルタ・MIDI-CV | 54.4 秒 | 1.47 |
| つながっていない出力を写さない | 41.6 秒 | 1.93 |
| 単音の写しを短く | 37.4 秒 | 2.14 |

サーバーの中で書き出す場合(`performance.render`)は、ブラウザのタブが同時に音声を計算していると、その分だけ遅くなる。変更前に、タブを動かしたまま測った値は 128 秒だった(変更後は未測定)。

## 4. まだ残っている負荷(変更後の内訳。41 モジュールの書き出し)
エンジンの写し 約 19%、発振器 約 14%、フィルタ 約 13%、アンプ 約 9%、残りは各モジュール。

これ以上速くするには、結果が変わりうる変更(つながっていない出力の波形を計算しない、ブロック単位で処理する)が要る。前者は、スナップショットや計測値に出る値が変わる。後者は「1 サンプル同期実行」という決定(DEC-108)に関わる。どちらも、やるなら決定が要る。

## 5. 高速化の後の再測定(2026-11-25、Issue #48)
同じ種類の作業用コンテナ(共用)で、高速化の後(PR #47 を含む main)を測った。高速化の前の値は、2026-11-23 の測定(`20261123-performance-measurement.md`)。日が違うので、機械の混み具合の差を含む。

### 5.1 ブラウザでの負荷(`npm run bench:browser`。音声スレッドの中で測定。平均。1.0 が実時間の限界)
| パッチ | モジュール | 前(11-23)平均 | 後(11-25)平均 | 後: 1.0 を超えたブロック | 後: 音声の時計の進み ÷ 実時間 |
|---|---|---|---|---|---|
| BP-0 | 1 | 0.009 | 0.007 | 0 / 3748 | 1.001 |
| BP-1 | 6 | 0.055 | 0.047 | 0 / 3749 | 1.001 |
| BP-POLY(16 声) | 6 | 0.245 | 0.179 | 4 / 3732 | 1.000 |
| BP-ALL | 18 → 20 | 0.154 | 0.143 | 2 / 3745 | 1.001 |
| BP-N N=1 | 4 | 0.036 | 0.028 | 0 / 3750 | 0.999 |
| BP-N N=2 | 8 | 0.078 | 0.062 | 2 / 3736 | 1.000 |
| BP-N N=4 | 14 | 0.154 | 0.119 | 0 / 3753 | 1.000 |
| BP-N N=8 | 28 | 0.301 | 0.206 | 7 / 3747 | 0.999 |
| BP-N N=16 | 54 | 0.562 | 0.347 | 32 / 3749 | 1.000 |
| BP-N N=32 | 108 | 0.973 | 0.698 | 528 / 3732 | 0.998 |
| BP-N N=64 | 214 | 1.841 | 1.314 | 2626 / 2759 | 0.739 |

- 54 モジュールの平均の負荷は 0.56 → 0.35。
- 108 モジュールは、前は音が途切れ始めていた(時計の比 0.984、超過 1635 回)。後は時計の比 0.998、超過 528 回。平均では収まるが、7 回に 1 回のブロックが間に合っていないので、**途切れずに鳴らせるとは言えない**。
- 214 モジュールは、後も実時間に収まらない(時計の比 0.739)。
- BP-ALL は、モジュールが 18 種から 20 種に増えたので、同じパッチの比較ではない。
- 生データ: `docs/perf/20261125-container/browser.json`。

### 5.2 サーバーの中での書き出し(`performance.render`。41 モジュール、80.2 秒の音声)
| 条件 | 所要 | 実時間の何倍の速さ |
|---|---|---|
| タブなし(サーバーだけ) | 30.8 秒 | 2.6 |
| タブで 41 モジュールの音声が動作中(演奏なし) | 29.9 秒 | 2.7 |
| タブで同じ曲を演奏中 | 31.0 秒 | 2.6 |

- タブが音声を計算していても、書き出しの所要時間は変わらなかった(書き出しは別スレッドで、4 コアの機械では競合しない)。演奏中のタブに、最終クリップ・非有限値は出なかった。
- 高速化の前に測った 128 秒は、タブを 2 倍の解像度で開き、画面の画像を撮りながらの値だった。同じ条件ではないので、128 秒 → 31 秒をそのまま高速化の効果とは言えない。同じ条件(単独実行)での効果は、§3.1 の 62.6 秒 → 37.4 秒。
- §3.1 の 37.4 秒(11-24)と、ここの 30.8 秒(11-25)の差は、測った日の機械の混み具合による。

## 6. 確認していないこと
- オーナーの手元の機材での値(OPEN-001)。
- コアの少ない機械で、タブの演奏と書き出しを同時に行った場合。
