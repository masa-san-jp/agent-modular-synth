# 性能の測定(遅延・負荷)

- 測定日: 2026-11-23
- 対象: Issue #32。検証計画 §7(VER-NF-004 負荷、VER-NF-005 遅延)
- **合否は出していない。** 遅延・負荷の目標は未決(OPEN-001)で、この文書は目標を決めるための材料である。

## 1. 結論
1. **この作業環境では、連鎖 16 本(54 モジュール)までは安定して鳴り、32 本(108 モジュール)で音切れが始まった。** 製品の上限(256 モジュール)は、この環境では鳴らしきれない。
2. **測定の途中で、エンジンの無駄を見つけて除いた。処理は約 3.3 倍速くなった**(出力は 1 ビットも変わっていない)。上の数字は、除いた後のもの。
3. **操作の遅延は小さい。** エージェントの要求の往復は中央値 3 ms 前後、音声側が変更を適用するまで平均約 6 ms。
4. **この環境は目標を決める機材ではない。** 共用のサーバー上のヘッドレスのブラウザで、音の出る機材もない。オーナーの手元の機材で同じ測定を行う必要がある(4 章)。

## 2. 測定環境
| 項目 | 値 |
|---|---|
| 機材 | 作業用のクラウドのコンテナ(共用)。Intel Xeon 2.10 GHz、4 コア、メモリ 16 GiB |
| OS | Linux x64 |
| ブラウザ | Chromium 153(ヘッドレス。音声の出力機材なし) |
| Node.js | v22.23.4 |
| サンプルレート / ブロック長 | 48000 Hz / 128 サンプル(1 ブロック = 2.667 ms) |
| 測定区間 | 準備 2 秒を捨てた後の 10 秒 |
| 生データ | `docs/perf/20261123-container/offline.json`、`browser.json` |

**負荷値** = 1 ブロックの処理時間 ÷ 1 ブロックの再生時間。1.0 を超えたブロックは、実時間に間に合っていない。

## 3. 結果

### 3.1 負荷(ブラウザ。VER-NF-004)
音声スレッドの中で、ブロックごとの処理時間を測った。

| パッチ | モジュール | 負荷 平均 | 99% | 1.0 を超えたブロック | 音声の時計の進み ÷ 実時間 |
|---|---|---|---|---|---|
| BP-0(空) | 1 | 0.009 | 0.40 以下 | 0 / 3752 | 1.000 |
| BP-1(基本の 1 声) | 6 | 0.055 | 0.40 以下 | 1 / 3749 | 1.001 |
| BP-POLY(16 声) | 6 | 0.245 | 0.40 以下 | 11 / 3736 | 1.000 |
| BP-ALL(18 種を各 1 個) | 18 | 0.154 | 0.40 以下 | 5 / 3749 | 0.999 |
| BP-N N=1 | 4 | 0.036 | 0.40 以下 | 0 / 3738 | 1.000 |
| BP-N N=2 | 8 | 0.078 | 0.40 以下 | 4 / 3740 | 1.000 |
| BP-N N=4 | 14 | 0.154 | 0.40 以下 | 2 / 3749 | 1.000 |
| BP-N N=8 | 28 | 0.301 | 0.80 以下 | 19 / 3735 | 1.000 |
| BP-N N=16 | 54 | 0.562 | 1.15 以下 | 77 / 3740 | 1.000 |
| **BP-N N=32** | 108 | **0.973** | 1.90 以下 | 1635 / 3688 | **0.984** |
| BP-N N=64 | 214 | 1.841 | 3.40 以下 | 1984 / 1984 | 0.530 |

- 「音声の時計の進み ÷ 実時間」が 1 を下回ると、処理が間に合わず、音が途切れている。**N=32 で途切れ始め、N=64 では半分しか進まない。**
- 単発の超過(BP-1 の 1 回など)は、共用の機材の割り込みによるものと見ている。時計の比は 1.000 のままで、連続した途切れにはなっていない。
- 99% の値が粗いのは、この環境の音声スレッドで使える時計が 1 ms 刻み(`Date.now`)だからである。平均と「超えたブロックの数」は信頼できるが、パーセンタイルは 0.4 刻みの目安にとどまる。高精度の時計が使える環境では、その値が自動で使われる。

### 3.2 負荷(オフライン。エンジン単体)
ブラウザを使わず、同じエンジンで 128 サンプルずつ処理した時間。高精度の時計で測れる。

| パッチ | モジュール | 負荷 中央値 | 95% | 99% | 実時間の何倍で処理できるか |
|---|---|---|---|---|---|
| BP-0 | 1 | 0.006 | 0.007 | 0.019 | 158.7 |
| BP-1 | 6 | 0.055 | 0.094 | 0.134 | 17.2 |
| BP-POLY | 6 | 0.224 | 0.338 | 0.404 | 4.1 |
| BP-ALL | 18 | 0.139 | 0.222 | 0.309 | 6.4 |
| BP-N N=8 | 28 | 0.333 | 0.452 | 0.504 | 3.1 |
| BP-N N=16 | 54 | 0.641 | 0.816 | 0.877 | 1.7 |
| BP-N N=32 | 108 | 0.972 | 1.574 | 1.855 | 0.9 |
| BP-N N=64 | 214 | 1.961 | 3.224 | 3.553 | 0.5 |

ブラウザでの値とほぼ同じである。この製品の負荷は、ほぼエンジンの計算で決まっている(ブラウザ側の上乗せは小さい)。

### 3.3 種別ごとの負荷(BP-M)
その種別だけを 64 個置いたときの負荷から、駆動用の分を引いて 64 で割った値。**1 個あたりの負荷値**(1000 分の 1 単位)。

| 種別 | 1 個あたり(×0.001) | 種別 | 1 個あたり(×0.001) |
|---|---|---|---|
| MOD-FLT-001 フィルタ | 16.0 | MOD-AMP-001 VCA | 6.4 |
| MOD-OSC-001 VCO | 12.3 | MOD-LGC-001 論理 | 6.1 |
| MOD-IO-002 MIDI-CV | 11.7 | MOD-DLY-001 ディレイ | 6.0 |
| MOD-MIX-001 ミキサー | 10.3 | MOD-IO-003 メーター | 5.9 |
| MOD-LFO-001 LFO | 10.1 | MOD-SEQ-001 シーケンサ | 5.2 |
| MOD-ENV-001 ADSR | 9.1 | MOD-CLK-001 クロック | 4.9 |
| MOD-CLK-002 分周 | 8.9 | MOD-NSE-001 ノイズ | 4.2 |
| MOD-FNC-001 関数発生器 | 8.1 | MOD-UTL-001 アッテヌバータ | 3.4 |
| MOD-RND-001 S&H | 6.7 | | |

- 読み方: フィルタ 1 個で、この環境の 1 ブロックの時間の約 1.6% を使う。フィルタだけなら約 60 個で 1.0 に達する。
- 最も軽いアッテヌバータ(掛け算と足し算だけ)でも 0.34% かかる。**計算そのものより、1 サンプルごとに全モジュールを順に呼ぶ仕組みの手間が大きい**ことを示している。
- 重い順は、フィルタ(毎サンプルの三角関数と指数関数)、VCO(指数関数と 4 波形)。

### 3.4 遅延(VER-NF-005)
BP-1 を鳴らしながら、`param.set` を不規則な間隔で 100 回送った。

| 区間 | 内容 | 中央値 | 95% | 最大 |
|---|---|---|---|---|
| L4 エージェントの往復(HTTP) | 要求を送ってから応答を受け取るまで | 2.7 ms | 4.6 ms | 13.2 ms |
| L4 エージェントの往復(MCP) | 同上。MCP アダプタ経由 | 3.1 ms | 6.2 ms | 46.0 ms |
| L2 音声側の適用 | タブが変更を送ってから、音声スレッドが適用するまで | 平均 5.7 ms | — | 10 ms |
| L3 出力 | ブラウザが報告する値(計算値) | baseLatency 10.0 ms + outputLatency 32 ms | | |
| L5 端から端 | 操作から実際の音の変化まで | **未測定**(録音の機材がない) | | |

- エージェントの操作が音に届くまでは、L4 の片道 + L2 + L3 で、おおよそ **50 ms 前後**と見積もれる。大半は L3(ブラウザと機材の出力の遅れ)で、機材によって変わる。この環境の L3 は、機材のない仮の出力の値である。
- L2 が 1 ブロック(2.7 ms)より長いのは、ブラウザが音声を約 10 ms 分まとめて処理するためである(baseLatency と同じ長さ)。
- L2 の時計は 1 ms 刻み。
- 楽譜による演奏(`score.play`)は、これらの遅延の影響を受けない。音符は音声側のサンプルの位置で予約するので、遅れるのは「最初の音が鳴り始めるまで」(0.1 秒の余裕)だけである。

## 4. 手元の機材で測る方法
目標を決めるには、実際に使う機材での値が要る(検証計画 §7.2: 性能の異なる機材 2 台以上)。

```
npm install
npm run bench            # オフライン(エンジン単体)。約 5 分。結果: bench/results/offline.json
npm run bench:browser    # ブラウザ。約 3 分。結果: bench/results/browser.json
```

- `npm run bench:browser` は、ヘッドレスの Chromium で測る。画面を出して実際の出力機材で測るには `BENCH_HEADED=1 npm run bench:browser`。
- 測るときは、ほかのアプリを閉じ、電源につなぐ。
- 出た JSON を渡してもらえれば、この文書と同じ表にまとめる。

## 5. 測定の途中で行った改善
最初の測定で、連鎖 16 本(54 モジュール)がオフラインで実時間に間に合わなかった(負荷の中央値 1.35)。原因を調べ、エンジンの無駄を除いた。

| 無駄 | 対処 |
|---|---|
| 毎サンプル、入力 1 つごとに、接続先を名前(文字列)で引いていた | 構成が変わったときにだけ手順の表を作り、毎サンプルは表をたどる |
| パラメータを読むたびに、定義の検索と値の正規化をしていた | 正規化後の値を控え、設定されたときだけ計算し直す |
| ケーブルの値を写すとき、常に 16 チャンネル分を写していた | 使っているチャンネルの分だけ写す |

| 連鎖 16 本(54 モジュール)の負荷の中央値 | 値 |
|---|---|
| 改善前 | 1.35(間に合わない) |
| 改善後 | 0.64 |

- 出力は変わっていない: 仕様の検証例 254 件と、ビット同一を確かめる試験がすべて通っている。
- 改善前の値は、短い測定区間(2 秒)での値である。

## 6. 目標を決めるための材料と、次の選択肢
決めるのはオーナーである(検証計画 §7.2 の3)。目標の案は、この文書の側からは固定しない。考える材料だけを挙げる。

- **上限との関係**: 製品の上限は 256 モジュールだが、この環境で鳴るのは 50〜100 個である。速い機材なら数倍は伸びるが、256 個すべてがフィルタや VCO なら、どの機材でも厳しい可能性がある。
- **実際の使い方**: デモ用のパッチは 6 モジュール(負荷 0.06)、18 種すべてを使うパッチでも 0.15 で、余裕は大きい。数十モジュールまでの普通のパッチは問題なく鳴る。

速くする手段は 3 つある。目標が決まってから選ぶのがよい。

| 手段 | 見込み | 手間・危険 |
|---|---|---|
| A. パラメータの読み方をさらに軽くする(名前で引くのをやめる) | 1〜2 割 | 小。18 モジュールを機械的に書き換える。出力は変わらない |
| B. 出力のないモジュールを処理しない、定数の入力を先に計算する、など | パッチによる | 中。仕様(全モジュールを毎サンプル処理する)との関係を整理する必要がある |
| C. 重いモジュールを WebAssembly にする(DEC-102 で想定済みの手段) | 数倍の可能性 | 大。ビット同一を保つための検証が要る |

## 7. 確かめられなかった点
- 実際に使う機材での値(この測定は共用のサーバー上)。
- 実際の出力機材での音切れ(ヘッドレスのブラウザには出力機材がない)。
- 端から端の遅延(L5。録音の機材が要る)。
- 画面を操作している状態での負荷(検証計画の手順 6)。ヘッドレスでは意味のある値にならない。
- Chromium 以外のブラウザ。
- 5 回の繰り返し(検証計画の手順 5)。今回は各 1 回。値のばらつきは、共用の機材では大きい。
- メモリの使用量。
