# 高速化の後の再測定(ブラウザでの負荷、サーバーの中での書き出し)

- 測定日: 2026-11-24、2026-11-25(繰り返し、原因の切り分け、描き直しの修正の後)
- 対象: Issue #48(引き継ぎ文書の A・B)。PR #47 のエンジンの高速化の後に、ブラウザの中とサーバーの中で測り直した。
- **合否は出していない。** 遅延・負荷の目標は未決(OPEN-001)。この文書は、目標を決めるための材料である。

## 1. 結論
1. **ブラウザの中でも、エンジンの高速化がそのまま効いている。** 連鎖 16 本(54 モジュール)の負荷の平均は 0.562 → 0.351。
2. **108 モジュール(連鎖 32 本)が、ブラウザで実時間に収まるようになった。** 高速化の前は音声の時計が遅れ(0.984)、音が途切れていた。今回は 1.000。214 モジュールは、まだ間に合わない(0.714)。
3. **タブで音声を動かしたままでも、サーバーの中での書き出しはほとんど遅くならない。** 41 モジュール・93.4 秒の音声の書き出しにかかった時間は次のとおり。
   - タブなし: 37.7 秒
   - タブで同じパッチを鳴らしたまま: 38.5 秒(2 % 増)
   - 書き出しの間も、タブの音声は途切れなかった(時計の比 1.000)
   - 高速化の前に測った 128 秒(タブで音声を動かしたまま)のような遅れは、出なかった
4. 書き出したファイルは、どの条件でも同じだった(MD5 が一致)。タブなし・タブあり・サーバーを使わないコマンド(`npm run render`)、さらに**高速化の前のコード**でも同じである。
5. **高速化の前のコードでも、128 秒は再現しなかった。** 同じ曲・同じ手順で、タブなし 60.5 秒、タブあり 63.5 秒(5 % 増)。128 秒は、そのときの共用の機材の混み具合など、コード以外の要因によるものと見る。
6. **MCP の往復が伸びていた原因を突き止め、直した。** 2.3 ms → 7.0 ms に伸びたのは、PR #43(画面の単色ウォッシュとラックの表示)からである。タブがエージェントに応答を返す前に、画面全体を描き直していた。描き直しを応答の後に回し、画面の更新 1 回分にまとめた。中央値は 2.3〜2.5 ms に戻った(§3.2)。

## 3. 結果

### 3.1 負荷(ブラウザ。`npm run bench:browser`)
**負荷値** = 1 ブロックの処理時間 ÷ 1 ブロックの再生時間。1.0 を超えたブロックは、実時間に間に合っていない。

| パッチ | モジュール | 負荷 平均(前回 → 今回) | 1.0 を超えたブロック(今回) | 音声の時計の進み ÷ 実時間(前回 → 今回) |
|---|---|---|---|---|
| BP-0(空) | 1 | 0.009 → 0.008 | 0 / 3733 | 1.000 → 1.000 |
| BP-1(基本の 1 声) | 6 | 0.055 → 0.049 | 1 / 3734 | 1.001 → 1.000 |
| BP-POLY(16 声) | 6 | 0.245 → 0.192 | 6 / 3743 | 1.000 → 1.000 |
| BP-ALL(全種を各 1 個) | 18 → 20 | 0.154 → 0.149 | 1 / 3741 | 0.999 → 1.001 |
| BP-N N=1 | 4 | 0.036 → 0.037 | 0 / 3746 | 1.000 → 0.999 |
| BP-N N=2 | 8 | 0.078 → 0.064 | 0 / 3733 | 1.000 → 0.999 |
| BP-N N=4 | 14 | 0.154 → 0.108 | 2 / 3746 | 1.000 → 0.999 |
| BP-N N=8 | 28 | 0.301 → 0.189 | 0 / 3739 | 1.000 → 1.000 |
| BP-N N=16 | 54 | 0.562 → **0.351** | 18 / 3733 | 1.000 → 1.000 |
| BP-N N=32 | 108 | 0.973 → **0.687** | 124 / 3751 | **0.984 → 1.000** |
| BP-N N=64 | 214 | 1.841 → 1.377 | 2660 / 2660 | 0.530 → 0.714 |

- **BP-ALL の数え方**: 前回の後にモジュールが 2 種増えた(MOD-SAT-001、MOD-MIX-002)。そのため BP-ALL は 18 → 20 モジュールで、そのままは比べられない。
- **N=32 で 1.0 を超えたブロック**: 124 個(3 %)あった。それでも時計の比は 1.000 で、続けて遅れることはなかった。ブラウザは約 10 ms 分をまとめて処理するので、単発の超過は吸収される。ただし、余裕は小さい。
- **パーセンタイル**: 前回と同じく、この環境の音声スレッドの時計は 1 ms 刻みである。99 % の値は 0.4 刻みの目安にとどまる。
- **繰り返し(6 回)**: 表の「今回」は 1 回目の値である。6 回の平均の範囲は次のとおり。6 回とは、修正前の 4 回と、描き直しの修正の後の 2 回である。修正の前後で差は見えず、揺れの範囲である。

| パッチ | 負荷 平均の範囲(6 回) | 時計の比の範囲 |
|---|---|---|
| BP-N N=16(54 モジュール) | 0.351〜0.432 | 0.999〜1.000 |
| BP-N N=32(108 モジュール) | 0.687〜0.781 | 0.999〜1.000 |
| BP-N N=64(214 モジュール) | 1.377〜1.532 | 0.640〜0.714 |

- **ほかのブラウザ**: この環境には Chromium しか入っておらず、入れることもできない(環境の決まり)。Firefox・Safari での値は、オーナーの手元で測る(Issue #50)。

### 3.2 遅延(ブラウザ。同じ測定)
| 区間 | 前回(2026-11-23) | 修正前(4 回) | 描き直しの修正の後(2 回) |
|---|---|---|---|
| エージェントの往復(HTTP)中央値 | 2.7 ms | 2.9〜3.1 ms | 1.9〜2.0 ms |
| エージェントの往復(MCP)中央値 | 3.1 ms | **7.0〜7.2 ms** | **2.3〜2.4 ms** |
| エージェントの往復(MCP)95 % | 6.2 ms | 9.0〜12.6 ms | 7.9〜9.8 ms |
| 音声側の適用 平均 | 5.7 ms | 4.6〜5.0 ms | 4.5〜5.2 ms |

**MCP の往復が伸びた原因**(2026-11-25 に切り分け)
- **コードの変更が原因と確かめた**: 同じ環境で、最初の測定のときのコード(1d254f4)を測ると 2.3 ms だった。機材の揺れではない。
- **二分探索で、伸びた版を特定した**(各版で 1 回、`BENCH_SECONDS=1`)。

| 版 | MCP 中央値 |
|---|---|
| a7491c5(#36) | 3.0 ms |
| 06231ce(#42) | 3.2 ms |
| **0ca6f71(#43 画面の単色ウォッシュ、ラックの表示)** | **10.4 ms** |
| 5f89b3f(#44) | 9.2 ms |
| d96206e(#45) | 7.3 ms |

- **原因**: タブは、パッチが変わった通知を受けるたびに、画面全体(ラックを含む)をその場で描き直していた。この描き直しは、エージェントへの応答を返す前に行われていた。
- **MCP だけ大きく伸びた理由**: 測定では、MCP の要求を間を空けずに続けて送る。そのため、次の要求が前の描き直しも待つ。HTTP の測定は要求の間を空けるので、伸びが小さかった。
- **修正**(`src/web/main.ts`。画面の中身と計算は変わらない)
  - 描き直しを、応答を返した後に回す。
  - 描き直しを、画面の更新 1 回分(1 フレーム)にまとめる。
  - 裏に回ったタブは、画面の更新が止まるので、0.25 秒ごとに描く。
- **修正の段階ごとの値**: 応答の後に回すだけでは 4.7 ms だった。1 フレームにまとめて 2.5 ms になった。

### 3.3 サーバーの中での書き出し(`npm run bench:render`)
曲は `demo/techno.mjs`(41 モジュール、楽譜 6 個、演奏の長さ 91.4 秒 + 余韻 2 秒 = 93.4 秒)。

| 条件 | 所要 | 実時間の何倍の速さ |
|---|---|---|
| サーバーを使わないコマンド(`npm run render`) | 38.5 秒(`time` の値) | 2.43 |
| サーバー、タブなし | 37.7 秒 / 38.4 秒 | 2.48 / 2.43 |
| サーバー、タブで同じパッチの音声を動かしたまま | 38.5 秒 / 39.1 秒 | 2.42 / 2.39 |
| 同、3 回目(描き直しの修正の後): タブなし / タブあり | 41.3 秒 / 40.6 秒 | 2.26 / 2.30 |
| 2 件を同時に頼む(タブあり) | 1 件目 41.1 秒、2 件目 81.8 秒 | — |
| **高速化の前のコード**(d96206e): タブなし / タブあり | 60.5 秒 / 63.5 秒 | 1.54 / 1.47 |

- **繰り返し**: サーバーでの 2 条件は、3 回測った。タブありとタブなしの差は −2〜+2 % で、揺れの範囲だった。
- **2 件を同時に頼んだとき**: 書き出しは 1 件ずつ順に行う作りである(`src/server/render-jobs.ts`)。2 件目は 1 件目の終わりを待つので、ほぼ 2 倍の時間で終わる。
- **曲の版**: 前回の値(62.6 秒 → 37.4 秒、80.2 秒の音声)とは、曲の版が違う。今の `demo/techno.mjs` は楽譜が 6 個で長さも違うので、所要時間の比較は「実時間の何倍の速さ」で見る(前回の高速化の後は 2.14 倍、今回は 2.4 倍前後)。
- **128 秒との違い**: 高速化の前は、タブで音声を動かしたまま 128 秒かかった、という記録がある。そこで、高速化の前のコード(d96206e)を同じ曲・同じ手順で測り直した。結果はタブなし 60.5 秒、タブあり 63.5 秒で、128 秒は再現しなかった。
  - タブの音声と書き出しは、別のコア(別スレッド)で動く。この 4 コアの機材では、互いの邪魔はわずか(5 % 以下)である。
  - 128 秒は、そのときの共用の機材の混み具合など、コード以外の要因と見る。
  - 当時の手順と演奏データは残っていないので、同じ条件では再現できない。
- **書き出しの間のタブの音声**: 時計の比は 1.000 で、途切れなかった。
- **書き出したファイル**: すべての条件で、高速化の前のコードを含めてバイト同一だった(MD5 `c463729cc42c273cbaf81eab0ce77ae2`)。

## 4. 測り方(手元の機材で繰り返すとき)
```
npm install
npm run bench:browser   # ブラウザでの負荷と遅延。約 3 分。結果: bench/results/browser.json
npm run bench:render    # サーバーの中での書き出し。約 2 分。結果: bench/results/render.json
```
- `bench:render` は、まず `demo/make-performance.mjs` で曲の演奏データを作り、次の 2 つを続けて測る。
  - タブなしでの書き出し
  - タブで同じパッチの音声を動かしたままでの書き出し
- 結果の JSON を渡してもらえれば、この表にまとめる。

## 5. この作業環境では確かめられない点(オーナーの手元で行う。Issue #50)
- 手元の機材での値(OPEN-001)。
- 実際の出力機材での音切れ。ヘッドレスのブラウザには出力機材がない。
- Chromium 以外のブラウザ。この環境には入っておらず、入れることもできない。
