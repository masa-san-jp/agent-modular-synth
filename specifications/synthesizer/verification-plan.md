# 検証計画(VER)

版: 0.1 / 2026-11-13。要求は [requirements.md](requirements.md)(`REQ-…`)、構成・安全・環境は [product-spec.md](product-spec.md)、コマンド(`CMD-…`)・エラー(`ERR-…`)・通知(`EVT-…`)・受入例(`AX-…`)は [operation-contract.md](operation-contract.md)、保存形式(規則 `DAT-…`、検証規則 `DAT-V…`、無効な例 `DX-…`)は [data-contract.md](data-contract.md)、判断と未決は [plans/decisions.md](../../plans/decisions.md)(`DEC-…`/`OPEN-…`)、モジュール挙動と検証例(`TV-…`)は [specifications/modules/](../modules/README.md) が正本。本書はそれらの本文を複製せず、IDで参照する。

**シンセ本体は未実装である。本書は「実装ができたときに何をどう確かめるか」の計画であり、試験結果ではない。** 本書のどの項目も、現時点で「合格」ではない。

## 1. 方針

1. **検証IDは要求IDと同じ枝番**(`REQ-F-001` ↔ `VER-F-001`)。1つの要求を複数の観点で確かめるときは小項目(`VER-F-004a` 等)に分ける。親項目の合否は、全小項目の合否で決まる。
2. **区分を混ぜない。** 各項目は次の区分のどれか1つに属する。

   | 区分 | 確かめること | 合否の出し方 |
   |---|---|---|
   | 機能再現 | モジュール仕様(#2)・製品仕様どおりの値が出るか | 期待値との一致(許容誤差は各検証例に従う) |
   | 接続 | モジュール間の配線、制御側とエンジン、UI・エージェント・サーバー間のつながり | 状態・信号が契約どおり |
   | 異常系 | 無効な要求・壊れた入力に対する拒否と状態不変 | エラーコードと状態の不変 |
   | 再現性 | 同じ入力で同じ出力が出るか | ビット同一、または定めた許容誤差 |
   | 性能 | 遅延、CPU負荷 | **数値目標が未決(OPEN-001)。測定値を記録するだけで、合否を出さない** |
   | 音質 | エイリアシング、歪み、ジッパーノイズ等 | **数値目標が未決(OPEN-006)。測定値を記録するだけで、合否を出さない** |
   | 安全性 | 出力保護、緊急停止、認証、権限の境界 | 不変条件(出力範囲、拒否)が破れない |
   | 環境別 | ブラウザ・OSごとの動作 | 環境ごとの確認結果。対応環境の確定(OPEN-002)の材料 |

   機能再現の合格は、音質・性能の合格を意味しない。逆も同じ(COM-15、MOD-OSC-001 §6 の「機能の誤りではなく音質の性質」)。例: MOD-OSC-001 のノコギリ波は仕様どおりの値が出れば機能再現は合格で、折り返し雑音の量は音質の測定項目(VER-NF-007)で別に記録する。
3. **未決の値を満たしたと扱わない。** 目標値が未決の項目(§7 性能、§8 音質、VER-S-001/003/004 の設定値)は、「測定値を記録し、オーナーが目標を決める」までが本書の範囲である。目標が決まったら、本書に合否基準を持つ小項目を追加する(§7.4、§8.3)。
4. **自動化可否**の表記: `自動`(人手なしで繰り返し実行できる)/ `半自動`(実行は自動、準備や判定の一部が人手)/ `手動`(実機と人の操作が要る)。
5. **試験用の覗き窓は製品の機能を変えない。** 試験のために値を取り出す仕組み(デバイスへ渡す直前の値の記録、処理時間の計測)は試験用ビルドだけに置き、製品ビルドのコマンド・権限を増やさない(REQ-S-007 と矛盾させない)。

## 2. 試験環境の種別(TE)

各項目の「前提環境」はこの表のIDで示す。実行基盤(テストランナー、ブラウザ自動操作の道具)は固定しない(§11)。

| ID | 名称 | 構成 | 音声デバイス | 主な用途 |
|---|---|---|---|---|
| TE-1 | オフライン実行 | **エンジンのコードを、音声デバイスなし・ブラウザなしで直接実行する**(DEC-102 によりエンジンはTypeScriptで、Node.js上でも同じコードを動かせる。product-spec §5.5)。`fs` は試験が指定する | 不要 | 機能再現、再現性、音質測定、出力保護の不変条件 |
| TE-2 | 制御側の単体実行 | コマンド処理・パッチグラフ(product-spec §4)を、画面なしで実行する。エンジンはTE-1のものを直結、または記録用の代役 | 不要 | コマンド、履歴、リビジョン、異常系、保存形式 |
| TE-3 | 統合(自動操作) | ローカルサーバー+ブラウザ(自動操作)+試験用のエージェントクライアント(共通コマンドAPI、MCP) | 不要(無音デバイスまたは仮想デバイスで可) | UIとエージェントの同値性、同期、認証、権限、自動保存 |
| TE-4 | 実機 | 環境別マトリクス(§10)の各候補環境で、実ブラウザ・実デバイス・実MIDI機器 | 必要 | 環境別受入、遅延・負荷の実測、自動再生制限 |
| TE-5 | 文書・リポジトリ検査 | リポジトリの内容と依存関係の一覧 | 不要 | ライセンス、追跡 |

**TE-1 の成立条件(実装への要求。設計判断 VP-D1)**: (a) エンジンのモジュール実行・グラフ実行・出力保護のコードは、ブラウザ固有のAPIに依存しない部分として切り出し、AudioWorklet内とオフライン実行で**同じソース**を使う。試験専用の分岐を処理経路に入れない。(b) オフライン実行は、`fs`、ブロック長(1 と 128)、入力列・パラメータ変更・MIDIイベントのサンプル番号を指定でき、出力列と内部状態を取り出せる。(c) ブラウザ内での裏取りとして、同じコードを OfflineAudioContext 上のAudioWorkletで走らせる経路を持てるなら、抜き取りで結果を突き合わせる(OfflineAudioContextは通常スレッドで描画する: F-021-002、F-021-022。AudioWorkletがOfflineAudioContextで使えるかは環境別試験 EC-01 で確認する)。

## 3. 記録する項目(全試験共通)

試験結果には次を必ず残す。性能・音質・環境別はこれがないと比較できない。

| 記録項目 | 内容 |
|---|---|
| 対象の版 | 製品のコミットID、モジュール仕様の版(各 `MOD-…` と common.md の版)、パッチ形式の版 |
| 実行環境 | TE種別。OS名と版、ブラウザ名と版、Node.jsの版、CPU型番・コア数、メモリ量、電源状態(バッテリー駆動か)、他の負荷の有無 |
| 音声設定 | 要求したサンプルレートと実際に得た `fs`(DEC-107)、ブロック長、`latencyHint` の指定値、`baseLatency`、`outputLatency`(F-021-009、F-021-010)、出力デバイス名と種類(内蔵/USB/Bluetooth等) |
| 試験条件 | 検証ID、入力(パッチ、コマンド列、MIDI列)の識別子、乱数seed、試行回数、測定区間 |
| 結果 | 測定値(生データの保存場所)、合否(区分が性能・音質のときは「記録のみ」)、逸脱と所見 |

## 4. 機能再現・接続・異常系(REQ-F)

### VER-F-001 モジュールの追加・削除
- **目的**: モジュールを追加・削除でき、状態が契約どおりになる。
- **区分**: 接続 / 異常系(小項目で分ける)。**対応要求**: REQ-F-001。
- **前提環境**: TE-2(状態)、TE-1 直結(エンジンへの反映)。
- **入力**: `module.add`、`module.remove`。対象は product-spec §6 の18種すべて。
- **手順と期待結果**:
  - **VER-F-001a(接続)**: 空のパッチ(MOD-IO-001 のみ)から18種を1つずつ `module.add` する。期待: 各応答が成功と新しいリビジョンを返し、`patch.get` にそのモジュールが既定パラメータ(各仕様 §4)で現れる。エンジン側は初期状態(各仕様 §5、COM-10)から動き始める。
  - **VER-F-001b(接続)**: ケーブルが付いたモジュールを `module.remove` する。期待: モジュールと、それにつながるケーブルがすべて外れ、応答の `removed_cable_ids` と一致する(CMD-03)。接続先だった入力は未接続時の値(COM-09)に戻る。
  - **VER-F-001c(異常系)**: 存在しない種別の追加(ERR-101)、存在しないIDの削除(ERR-102)、常設の `out`(MOD-IO-001)の削除(ERR-104、AX-10d)、MOD-IO-001 の2個目の追加(ERR-105)、使用中のIDの指定(ERR-103)、書式に合わないID(ERR-003)。期待: 各エラーで拒否。リビジョンと `patch.get` の内容が要求前と同一。
  - **VER-F-001d(IDと `seed` の割当)**: IDを省略した追加は `m<N>` の連番になり、削除後も番号を再利用しない(operation-contract §2.2)。`seed` を持つ種別(MOD-NSE-001、MOD-RND-001)を `seed` 省略で2個追加すると 1、2 が割り当てられ、重なる値を指定すると成功して `duplicate_seed` の警告が付く(operation-contract §14、AX-13)。割当はパッチの状態だけで決まる(同じ操作列なら同じ値)。
- **許容誤差**: 状態は完全一致。
- **測定方法**: 要求前後の `patch.get` の比較。エンジン側はオフライン実行でモジュール出力を読む。
- **自動化**: 自動。**合否**: 全ケースが期待どおり。

### VER-F-002 接続・切断
- **目的**: ケーブルの接続・切断ができ、信号が共通規約どおりに伝わる。型違いの接続が許可される。
- **区分**: 接続 / 異常系。**対応要求**: REQ-F-002。
- **前提環境**: TE-2+TE-1。
- **入力**: `cable.connect`、`cable.disconnect`。
- **手順と期待結果**:
  - **VER-F-002a(接続)**: MOD-OSC-001 の `sine` を MOD-IO-003 の `IN` につなぐ。期待: 接続先の入力が見る値は、接続元がそのステップで書いた値の**1サンプル後**(COM-06)。切断後は未接続時の値 0 V(COM-09)。
  - **VER-F-002b(接続)**: 型違いの接続(例: `audio` 出力の MOD-OSC-001 `saw` → `gate` 入力の MOD-ENV-001 `gate`)。期待: 成功し(COM-01)、応答の `warnings` に `type_mismatch` が入る(operation-contract §13.7)。接続先は値をそのまま閾値判定する(COM-04)。型が同じ接続には警告が付かない。
  - **VER-F-002c(接続)**: 正規化のある入力。MOD-IO-001 の `IN_R` は未接続のとき `IN_L` の値を使い(各仕様 §3)、`IN_R` に接続すると正規化が切れ、切断すると戻る(COM-09)。
  - **VER-F-002d(分岐)**: 1つの出力から複数の入力へつなげる(operation-contract §13.3)。各接続先が同じ値を見る。
  - **VER-F-002e(異常系)**: 無効接続(operation-contract §13)。方向の誤り(入力→入力、出力→出力: ERR-112、AX-02a)、既にケーブルがある入力への接続と同じ接続の重複(ERR-114。`same_source` の真偽を確認。AX-02b)、接続できないポート(MOD-IO-001 の `DEV_L`/`DEV_R`、MOD-IO-002 の `MIDI`: ERR-113、AX-02c)、存在しないモジュール・ポート(ERR-102、ERR-111、AX-03b)、存在しないケーブルの切断(ERR-115、AX-03c)、使用中のケーブルID(ERR-116)、`cable.disconnect` の引数の両方指定・指定なし(ERR-003)。期待: 各エラーで拒否され、状態は不変。
- **許容誤差**: 状態は完全一致。信号は各モジュールの検証例の許容誤差。
- **測定方法**: オフライン実行で接続元・接続先の値をステップごとに記録して突き合わせる。
- **自動化**: 自動。**合否**: 全ケースが期待どおり。

### VER-F-003 パラメータ変更
- **目的**: パラメータを変更でき、次の処理ステップから出力に反映される。
- **区分**: 機能再現 / 異常系。**対応要求**: REQ-F-003。
- **前提環境**: TE-1(反映時刻)、TE-2(コマンド)。
- **入力**: `param.set`。
- **手順と期待結果**:
  - **VER-F-003a(機能再現)**: エンジン単体で、ステップ `n` の前にパラメータを変えると、ステップ `n` の出力から新しい値が使われる(COM-05、COM-13)。確認は、パラメータ変更を含む既存の検証例(例: TV-MOD-NSE-001-04、TV-MOD-NSE-001-10)で行う。
  - **VER-F-003b(接続)**: 制御側から `param.set` を送ったとき、エンジンでは**次のブロック先頭**から有効になる(product-spec §5.6)。期待: 変更が現れる最初のサンプルは、エンジンがメッセージを受け取った次のブロックの先頭。ブロックの途中からは変わらない。この遅れ(最大128フレーム)は遅延測定(VER-NF-005)に含める。
  - **VER-F-003c(異常系)**: 範囲外の値、NaN/∞、存在しないパラメータ名、存在しないモジュールID。期待: 外部操作層では**拒否**される(クランプしない。operation-contract §12): 範囲外は ERR-123(AX-04a)、数値でない値と NaN の代用は ERR-122(AX-04b、AX-04c)、整数型・列挙型・真偽型への非整数は ERR-122(AX-04d)、存在しないパラメータは ERR-121(AX-03d)、存在しないモジュールは ERR-102(AX-03a)。状態は不変で、値は丸められも切り詰められもしない。18種の全パラメータについて、範囲の両端(受理)と両端のすぐ外(拒否)を試す。他のパラメータや `fs` に依存する範囲(MOD-IO-003 の `pre`、MOD-DLY-001 の `time`)は、契約 §12.1 のとおり仕様の最大範囲で受理され、エンジンが仕様どおりクランプする。エンジンに直接届いた値に対するモジュールの扱い(範囲外はクランプ、NaN/∞は既定値。COM-12、COM-13)は別層で、各仕様の `無効入力` 種別の検証例(VER-F-004a)で確かめる。
  - **VER-F-003d(同じ値)**: 現在と同じ値の `param.set` は成功し、`changed: false`、リビジョン・履歴・通知は変わらない(operation-contract §4.3、AX-15)。
- **許容誤差**: 各検証例に従う。反映時刻はサンプル単位で完全一致。
- **測定方法**: オフライン実行。メッセージ到着ブロックと出力変化の最初のサンプル番号を記録。
- **自動化**: 自動。**合否**: 全ケースが期待どおり。

### VER-F-004 モジュール仕様の検証例(機能再現の中心)
- **目的**: 採用18モジュールの実装が、#2の各仕様 §10 の検証例(`TV-MOD-…`)をすべて満たす。
- **区分**: 機能再現。**対応要求**: REQ-F-004。
- **前提環境**: TE-1(音声デバイスなしでエンジンコードを直接実行)。
- **入力**: `specifications/modules/MOD-*.md` §10 の全TV(18仕様。件数は §12 の注記を参照)。各TVの前提(`fs`、パラメータ、初期状態)と入力列。
- **手順**:
  1. 試験ハーネスは、TVごとにモジュール1個を単体で生成する(COM-06: 単体の検証例は「そのステップで入力ポートが読む値 `x[n]` → そのステップで書く値 `y[n]`」。ケーブルの1サンプル遅延は入れない)。
  2. TVの前提どおりに `fs`・パラメータ・初期状態を設定する。省略値は `fs=48000` と各仕様 §4 の既定値(COM-15)。
  3. 入力列を1ステップずつ与える。パラメータ変更・`reset()`・保存復元・MIDIメッセージは、TVが指定するステップで行う。
  4. 出力(TVが指定するポート、内部状態、読出し値)を期待値と比べる。
  5. 同じTVを**ブロック長1と128の両方**で実行する(DEC-108、COM-05。両者の一致は VER-NF-003c で判定)。
- **期待結果・許容誤差**: **各TVの「許容誤差と根拠」列に従う**。判定式は `|y − expected| ≤ max(abs, rel·|expected|)`(COM-15)。「ビット同一」と書かれたTV(保存復元)はビット比較する(COM-14)。本書は許容誤差を上書きしない。
- **測定方法**: オフライン実行の出力列を数値比較。統計量・周波数を期待値にするTV(例: TV-MOD-NSE-001-03)は、TVに書かれた算出方法で求める。
- **小項目**:
  - **VER-F-004a**: 上記の全TVの実行(モノ)。
  - **VER-F-004b(網羅の検査)**: 仕様の §10 から機械的に列挙した全TV-IDが、試験結果に**1回ずつ**現れることを検査する。TVはMarkdownの表で書かれており、試験コードへの変換は人手になるため、抜けと、仕様改訂後の古い試験を検出する。期待: 仕様にあるTV-IDで結果がないもの、結果にあるが仕様にないもの、仕様の版が試験の作成時より新しいものが0件。
  - **VER-F-004c(仕様改訂への追随)**: #2の仕様が改訂されたとき(OPEN-003 の `run` 停止時の挙動、OPEN-004 のポリ検証例、OPEN-009 の設計仮定の見直し)、改訂後のTVで VER-F-004a/b を再実行する。改訂前のTVに合格していても、改訂後の合格とは扱わない。
- **自動化**: 自動(TVから試験コードへの変換は人手。VER-F-004b で抜けを検出)。
- **合否**: 全TVが許容誤差内、かつ VER-F-004b の不一致が0件。1件でも不合格・未実行なら不合格。

### VER-F-005 ポリフォニー
- **目的**: 1ケーブル最大16チャンネルで発音できる。
- **区分**: 機能再現。**対応要求**: REQ-F-005。
- **前提環境**: TE-1。
- **前提(blocking)**: **ポリ時の検証例は未作成(OPEN-004)。** #2の改訂で各仕様にポリ時のTV(COM-08 に従うチャンネル独立、加算系の例外、MOD-IO-002 のボイス割当規則)が追加されるまで、本項目は実行できない。モノの検証(VER-F-004a)は先に実行できる。
- **手順と期待結果(TV追加後)**:
  - **VER-F-005a**: 追加されたポリTVを VER-F-004 と同じ方法で実行する。許容誤差は各TVに従う。
  - **VER-F-005b(チャンネル独立の一般検査)**: チャンネル間の相互作用を持たないモジュールについて、`N` チャンネル(N=2, 16)の入力を与えた出力の各チャンネルが、同じ入力を1チャンネルで与えたモノ実行の出力と一致する(COM-08「チャンネルごとに独立に同じ式を適用」)。副入力は、1チャンネルなら全エンジンへコピー、不足チャンネルは 0 V。MOD-MIX-001 は加算系の例外(単音入力は1チャンネル目だけに寄与)。モノのみのポート(MOD-IO-001、MOD-IO-002 の出力、MOD-IO-003 は1チャンネル目のみ)は各仕様 §3 のとおり。
  - **VER-F-005c(境界)**: 17チャンネル以上の指定、チャンネル数0。期待はポリTVまたは operation-contract の定義に従う。
- **許容誤差**: VER-F-005b は同一環境でビット同一(各チャンネルが同じ式・同じ演算順のため。設計判断 VP-D2)。
- **自動化**: 自動。**合否**: 追加TVの全合格と VER-F-005b/c の一致。**OPEN-004 が解消するまで「未実行」とし、合格と扱わない。**

### VER-F-006 MIDI入力
- **目的**: ノート、ピッチベンド、CC、クロックで演奏できる。
- **区分**: 機能再現(a)/ 接続(b, c)。**対応要求**: REQ-F-006。
- **手順と期待結果**:
  - **VER-F-006a(機能再現、TE-1)**: MOD-IO-002 §10 の全TVを、サンプル番号付きのメッセージ列として与える(VER-F-004a の一部。ここでは要求との対応を示す)。期待: `PITCH`/`GATE`/`VEL`/`PW`/`MOD`/`RTRG`/`CLK` が各TVどおり。
  - **VER-F-006b(接続、TE-1+制御側)**: メッセージのサンプル番号への割当。期待: 受信した処理ブロックの**先頭**のサンプルに割り当てられ、同じブロックに複数届いたときは到着順に処理される(product-spec §7.3、COM-07)。入力: 1ブロック内にノートオン→ノートオフ→ノートオンを届ける列、ブロック境界をまたぐ列。
  - **VER-F-006c(接続、TE-4)**: 実MIDI機器(または仮想MIDIポート)から鍵盤を弾き、MOD-IO-002 → MOD-OSC-001 → MOD-IO-001 のパッチで発音する。ノート60で `PITCH` が 0 V(COM-03)であることを `meter.read` で確かめる。Web MIDI非対応の環境では、MIDI機能が無効で、`engine.get_status` の `midi.available` が偽になる(product-spec §7.3、CMD-21)。パッチに MOD-IO-002 を2個置くと、両方が同じMIDI入力の列を受け、`channel` で振り分けられる(operation-contract §13.6)。初期版にはエージェントからノートを送るコマンドがない(operation-contract §6.1)ため、TE-3 でのMIDI入力は仮想MIDIポートから与える。
- **許容誤差**: (a) 各TV。(b) サンプル番号は完全一致。(c) 読出し値はMOD-IO-002のTVの許容誤差。
- **自動化**: (a)(b) 自動、(c) 手動(仮想MIDIポートを使えば半自動)。
- **合否**: 全ケースが期待どおり。(c) は環境別マトリクス(EC-03)に結果を記録する。ポリ割当は VER-F-005。

### VER-F-007 保存・復元
- **目的**: パッチを保存・復元でき、構成とパラメータが一致する。
- **区分**: 機能再現 / 異常系。**対応要求**: REQ-F-007。
- **前提環境**: TE-2(形式と状態)、TE-3(サーバー経由のファイル保存)。
- **入力**: `patch.save`、`patch.load`。試験パッチ: 18種を各1個以上含み、全パラメータを既定値以外に設定し、ケーブル(フィードバックを含む)を張ったもの。
- **手順と期待結果**:
  - **VER-F-007a(往復)**: 保存 → 空のパッチに復元 → `patch.get`。期待: 保存前と**一致**する。一致の定義は DAT-04(モジュールとケーブルをIDで対応づけ、種別・仕様版・全パラメータ・`ui`・接続・題名・説明を比べる。時刻・保存者・配列の順は比べない)。保存ファイルには全パラメータが書かれている(DAT-07)。
  - **VER-F-007b(再保存の安定)**: 復元したパッチをもう一度保存する。期待: DAT-04 の意味で1回目と一致。`ui` 内の未知のキーが保持されて書き戻される(DAT-11)。`created_at` が引き継がれ、`modified_at`・`saved_by` が保存のたびに書かれる(DAT-35)。
  - **VER-F-007c(復元後の音)**: パッチは内部状態を含まない(DAT-01)。期待: `patch.load` の直後、全モジュールが初期状態(COM-10)から始まり、乱数は `seed` パラメータから再シードされる。読込直後からの出力は、同じパッチを空の状態から組み立てて初期状態から動かした出力とビット同一で、何度読み込んでも同じ(REQ-NF-003)。読込前に鳴っていた音(遅延バッファ、フィードバックの残り)が読込後に出ない。内部状態を含めた続きの一致(COM-14 のビット同一)は、パッチではなく検証用スナップショットで確かめる(VER-NF-003b)。
  - **VER-F-007d(異常系)**: 壊れたJSON、必須項目の欠落、未知の種別(AX-12)、存在しないモジュールを指すケーブル、範囲外のパラメータ、大きすぎるパッチ(ERR-206)、未知の(新しい)版(ERR-205)、存在しない名前(ERR-202)。期待: 読込全体を拒否し(一部だけ読み込まない。DAT-40)、**現在のパッチ・リビジョン・履歴は不変**(product-spec SC-H3)。`details.issues` の `rule` に違反した規則が入る。**読込時の検証規則 DAT-V01〜DAT-V18 のすべて**について、それに反する入力を少なくとも1つ試し、試験に現れない規則を0件にする。無効な例 DX-01〜DX-12 を、データ契約に書かれた応答どおりであることまで含めて実行する。検証が段階順に行われる(前の段階が通らなければ次の段階の問題が報告されない)。
  - **VER-F-007h(補完)**: パラメータを省いたパッチは、その `spec_version` の既定値で補って読み込まれ、`param_defaulted` の警告が付く(DAT-08)。`seed` が重なるパッチは書かれた値のまま受理される。JSONを直接渡す読込(`patch` 引数)と名前での読込が同じ結果になる。
  - **VER-F-007e(保存先と一覧)**: 名前付き保存が専用フォルダ内にだけ作られる(境界の試験は VER-S-007b)。同名があるときは `overwrite` なしで ERR-203。`patch.list` に現れ、`patch.read` で中身が読める(読むだけで現在のパッチは変わらない)。壊れたファイルは一覧に `readable: false` で現れる。`patch.save` はリビジョン・履歴を変えない(operation-contract §4.2)。
  - **VER-F-007f(読込の取り消し)**: `patch.load`・`patch.new` の直後に `history.undo` すると、置き換え前のパッチに戻る(operation-contract §9.8)。
  - **VER-F-007g**: 受入例 AX-01 を実行する。
- **許容誤差**: 構成・パラメータは完全一致(数値はデータ契約が定める表現で往復後に同じ値)。
- **測定方法**: `patch.get` の比較、保存ファイルの比較、オフライン実行の出力比較。
- **自動化**: 自動。**合否**: 全ケースが期待どおり。操作契約・データ契約の受入例(§6.3)も実行する。

### VER-F-008 自動保存と再開
- **目的**: 作業中のパッチが自動保存され、再読込後に再開できる。
- **区分**: 接続。**対応要求**: REQ-F-008。
- **前提環境**: TE-3、TE-4(ブラウザごとの保存領域の挙動)。
- **手順**: (1) パッチを編集する(追加・接続・パラメータ変更)。(2) 自動保存の契機(リビジョンが進むたび。まとめ待ちは暫定1秒以内。タブが隠れる・閉じる直前に必ず書く: DAT-21)を待つ場合と、変更の直後に閉じる場合の両方を行う。(3) タブを再読込する。(4) タブを閉じて開き直す。(5) サーバーを再起動して開き直す。
- **期待結果**: (3)〜(5) のどれでも、直前のパッチ(構成・パラメータ)が復元される。**復元直後は音が出ない**(音声状態は `stopped`。product-spec §3.2)。リビジョンは続きの値から始まり、`session_id` は変わり、取り消しの履歴は消える(operation-contract §4.4、§9.7)。自動保存がない初回はリビジョン 0 の空のパッチ(`out` だけ。DAT-23)から始まる。自動保存に履歴・音量・緊急停止・内部状態が含まれない(DAT-22)。自動保存が壊れている・未知の版のときは、壊れたデータを退避して残し、空のパッチで起動し、UIに知らせる(DAT-24。退避データが消えていないこと)。旧版の自動保存は移行して読む。2つ目のタブを開くとセッションにならず、その旨が表示され、1つ目の自動保存を上書きしない(DAT-25)。待受ポートが変わると自動保存を引き継げない(データ契約 §7.1 の注意)ため、既定のポートで再起動して確かめる。
- **許容誤差**: `patch.get` が DAT-04 の意味で一致。変更の直後に閉じた場合も、最後の変更まで復元されること(取りこぼし0件)。
- **測定方法**: 再読込前後の `patch.get` の比較。
- **自動化**: 自動(TE-3)、環境別は半自動。**合否**: 全手順で一致。

### VER-F-009 取り消し・やり直し
- **目的**: UIとエージェントに共通の履歴で、操作を取り消し・やり直しできる。
- **区分**: 機能再現 / 異常系。**対応要求**: REQ-F-009。
- **前提環境**: TE-2、TE-3(UIとエージェントの混在)。
- **入力**: `history.undo`、`history.redo` と、各種の変更コマンド。
- **手順と期待結果**:
  - **VER-F-009a**: 変更コマンド(追加、削除、接続、切断、パラメータ変更、`batch`)を1つずつ実行し、直後に取り消す。期待: `patch.get` の構成・パラメータが実行前と一致する。やり直すと実行後と一致する。削除を取り消したとき、同じIDのモジュール・ケーブルとパラメータが戻る。**エンジンの内部状態は戻らず**、復活したモジュールは初期状態から始まる(operation-contract §9.5)。
  - **VER-F-009b**: `batch` は1回の取り消しで全体が戻る(product-spec SC-A1: 1リビジョンとして適用)。
  - **VER-F-009c**: 人の操作とエージェントの操作を交互に行い、取り消す。期待: 誰の操作でも直前の操作が戻り、応答の `undone` に元の操作者が入る(SC-X1、AX-11)。
  - **VER-F-009d(異常系)**: 履歴が空のときの取り消し(ERR-141)、やり直す対象がないときのやり直し(ERR-142)、取り消した後に新しい変更をした場合のやり直し(やり直し側が消えるため ERR-142)。状態は壊れない。
  - **VER-F-009e(リビジョン)**: 取り消し・やり直しでもリビジョンは 1 **進む**(戻らない)。通知 EVT-01 が出る(operation-contract §9.3)。
  - **VER-F-009f(履歴の規則)**: やり直しは記録済みの結果を再適用する(自動採番のIDと自動割当の `seed` が変わらない)。同じ `coalesce_key` の連続した `param.set` は履歴1件にまとまり、1回の取り消しで最初の変更の前の値に戻る。音量・緊急停止・ファイル保存は履歴に入らず、取り消しで音量が変わらない・緊急停止が解除されない(operation-contract §2.1、§9)。保持件数(暫定200件)を超えた古い履歴が捨てられる。再読込で履歴が消える。
- **許容誤差**: 完全一致。**自動化**: 自動。**合否**: 全ケースが期待どおり。

### VER-F-010 信号値の読出し
- **目的**: メーター・スコープの値を読み出せる。
- **区分**: 機能再現(a)/ 接続(b)。**対応要求**: REQ-F-010。
- **手順と期待結果**:
  - **VER-F-010a(TE-1)**: MOD-IO-003 §10 の全TV(VER-F-004a の一部)。読出し値(`level`、`peak`、`rms`、`mean`、`vmin`、`vmax`、`windows`、`peak_hold`、`nonfinite_count`、`frame`、`frame_seq`)が各TVどおり。
  - **VER-F-010b(TE-2+TE-1)**: 既知信号のパッチ(MOD-OSC-001 `sine` → MOD-IO-003 `IN`)で `meter.read` を呼ぶ。期待: 返る値が、同じ時点のエンジン内の MOD-IO-003 の読出し値と一致し、値がどの時点(窓の番号 `windows`、フレーム番号 `frame_seq`)のものかが分かる。値の基準は MOD-IO-003 §6 の式で独立に計算する。
  - **VER-F-010c(異常系)**: 存在しないID(ERR-102)、MOD-IO-003 以外を指定した読出し(ERR-303)、音声が `stopped`・`suspended` のときの読出し(ERR-301、AX-09b)、未知の項目名(ERR-003)。
  - **VER-F-010d(反映の確認)**: 返値の `engine_revision` が、エンジンに反映済みの最新リビジョンである。変更の直後は古い値が返りえ、反映後に追いつく(operation-contract §11.3)。`sample_time` と `fs` が返る。`frame` は `fields` で指定したときだけ返る。読出しが測定状態を変えない(続けて読んでも `windows` が読出しで進まない)。
- **許容誤差**: MOD-IO-003 の各TVの許容誤差。伝送で値が変わらないこと(契約が定める数値表現の範囲で一致)。
- **自動化**: 自動。**合否**: 全ケースが期待どおり。

### VER-F-011 フィードバック接続
- **目的**: ループを作れ、挙動が評価順序に依存せず定義される。
- **区分**: 接続 / 再現性。**対応要求**: REQ-F-011。
- **前提環境**: TE-1+TE-2。
- **手順と期待結果**:
  - **VER-F-011a(自己ループ)**: MOD-MIX-001 の `out` を自分の `in2` につなぎ、`in1` に既知の入力列を与える。期待: `out[n]` は、MOD-MIX-001 §6 の式に「`in2[n] = out[n−1]`(COM-06 のケーブル1サンプル遅延)」を入れた漸化式の値と一致する。ループ利得が1以上になる設定では、出力が ±12 V のクランプ(COM-02)で止まり、非有限値にならない。
  - **VER-F-011b(2モジュールのループ)**: MOD-DLY-001 と MOD-MIX-001 でループを作る(ポート名は各仕様 §3)。期待値は、各仕様の式とケーブル遅延1サンプル+モジュール内遅延(COM-06)から、実装と独立な参照計算で求める。
  - **VER-F-011c(評価順序)**: 同じパッチを、モジュールの追加順・ケーブルの接続順を変えて3通り以上作る。期待: 出力列が同一環境で**ビット同一**。
  - **VER-F-011d**: ループを作る `cable.connect` が拒否されず、ループであることを理由とする警告も出ない(operation-contract §13.5)。受入例 AX-07(MOD-FLT-001 の `out` → 自分の `cv2`)を実行し、接続後の出力が有限で、参照計算と一致することも確かめる。
- **許容誤差**: (a)(b) は関係するモジュールのTVの許容誤差を使う(漸化で誤差が積もる区間の長さと許容を、参照計算とともに試験に記す)。(c) はビット同一。
- **自動化**: 自動。**合否**: 全ケースが期待どおり。

### VER-F-012 まとめて適用(batch)
- **目的**: 複数の操作をまとめて適用でき、途中で失敗したら全体が取り消される。
- **区分**: 機能再現 / 異常系。**対応要求**: REQ-F-012。
- **前提環境**: TE-2、TE-3。
- **入力**: `batch`(追加・接続・設定の列)。
- **手順と期待結果**:
  - **VER-F-012a(成功)**: 追加3・接続3・設定3を1つの `batch` で送る。期待: 全て適用され、**リビジョンは1つだけ進む**。履歴は1件、通知 EVT-01 は1件。エンジンへは1つの差分として同じブロック境界で反映される(途中の構成の音が1サンプルも出ない)。同じ操作を1つずつ送った場合と構成・パラメータが一致(AX-08b)。
  - **VER-F-012b(部分失敗)**: 無効な操作を、列の先頭・中間・末尾に1つ入れた3通り。期待: **何も適用されない**。リビジョン・`patch.get`・履歴が要求前と同一。エンジンへ差分が送られていない(途中状態の音が出ない)。応答は ERR-131 で、`details.failed_index`(0始まり)と `details.cause` から、何番目の操作がどのエラーで失敗したかが分かる。通知は出ない(AX-08a)。
  - **VER-F-012c**: `batch` 内で、前の操作が `id` を指定して作ったモジュールを、後の操作が参照できる(CMD-09)。「外す → つなぐ」を1回の `batch` で行える(operation-contract §13.2)。
  - **VER-F-012d(境界・異常系)**: 空の `batch`(ERR-003)、上限件数(暫定500件)ちょうどと超過(ERR-106)、`batch` に入れられないコマンド(`batch` の入れ子、`patch.load`、`engine.panic` 等)を含む場合(ERR-132。何も検証・適用されない)。`expected_revision` と `idempotency_key` は `batch` 全体に1回だけ効く。
- **許容誤差**: 完全一致。**測定方法**: `patch.get` とリビジョンの前後比較、エンジンへ送られた差分メッセージの記録。
- **自動化**: 自動。**合否**: 全ケースが期待どおり。操作契約の batch 部分失敗の受入例(§6.3)を含む。

## 5. エージェント操作(REQ-A)

### VER-A-001 種別と定義の列挙
- **目的**: エージェントが、モジュール種別と各ポート・パラメータの定義を列挙できる。
- **区分**: 機能再現。**対応要求**: REQ-A-001。
- **前提環境**: TE-2。**入力**: `module.list_types`。
- **手順**: 列挙結果を、各モジュール仕様 §3(ポート: 名前、方向、型、チャンネル)と §4(パラメータ: 名前、単位、範囲、既定値)から機械的に抜き出した表と突き合わせる。
- **期待結果**: 18種すべてが現れる。ポート名・方向・型(`signal_type`)・未接続時の扱い、パラメータ名・種別(`kind`)・単位・範囲・既定値・列挙値、`spec_version` が仕様と一致する。仕様にない項目、欠けた項目が0件。大文字・小文字は仕様どおり(COM-18: 仕様ごとに異なる)。`singleton` は MOD-IO-001 だけ、`connectable: false` は operation-contract §13.6 のポートだけ、`readouts` は MOD-IO-003 だけ。添字付きパラメータ(MOD-SEQ-001)の名前が契約 §2.2 の書き方で列挙される。`type` 指定で1種だけ返り、未知の種別は ERR-101。タブがなくても応答する。列挙された範囲で `param.set` の受理・拒否が決まる(VER-F-003c と同じ定義表を使っていること)。
- **許容誤差**: 名前・型は完全一致。数値は同じ値。
- **自動化**: 自動(仕様の表からの抽出を含む)。**合否**: 不一致0件。

### VER-A-002 UIと同じコマンドで操作できる
- **目的**: エージェントが、画面クリックに依存せず、UIと同じコマンドで生成・削除、接続・切断、パラメータ変更、保存・復元を行える。
- **区分**: 接続。**対応要求**: REQ-A-002。
- **前提環境**: TE-3。
- **手順**: 同じ操作の筋書き(product-spec SC-H1 と SC-A1 に相当する、追加 → 接続 → 設定 → 保存 → 復元)を、(i) UIの自動操作、(ii) 共通コマンドAPI、(iii) MCPアダプタ(VER-A-007)の3経路で、それぞれ空のパッチから実行する。

### VER-A-005 再送と競合
- **目的**: 同じ要求の再送が二重適用されず、古い状態に基づく変更が競合として検出される。
- **区分**: 異常系。**対応要求**: REQ-A-005。
- **前提環境**: TE-2、TE-3。
- **手順と期待結果**:
  - **VER-A-005a(再送)**: 冪等キー付きの `module.add` を送り、同じキーで同じ要求をもう一度送る。期待: モジュールは1個だけ。2回目は保存済みの応答が `replayed: true` で返り、`request_id` は再送側の値、`revision` は最初の応答時の値。リビジョン・履歴・通知は1回分だけ(AX-05a)。
  - **VER-A-005b(応答を失った再送)**: 要求は適用されたが応答が届かなかった状況(試験側で応答を捨てる、接続を切って再接続する、タブの応答を遅らせて ERR-007 を起こす)で、同じキーで再送する。期待: 適用済みなら保存済みの応答、未適用なら新しく適用した応答が返り、どちらでも二重適用されない(operation-contract §7.4)。
  - **VER-A-005c(同じキーで別の内容)**: ERR-009 で拒否、状態不変(AX-05b)。
  - **VER-A-005d(キーの保持範囲)**: 失敗した応答は保存されず、同じキーの再送はあらためて評価される。保持件数(暫定1000件)を超えた古いキーの扱い、再読込(`session_id` の変化)をまたいだ再送が、operation-contract §7 のとおり(再読込後は保存済みの応答がないため、`expected_revision` を併用した再送が ERR-008 になり二重適用されないこと)。読出しコマンドと `engine.panic` ではキーが無視される。

  - **VER-A-005f**: 受入例 AX-05a、AX-05b、AX-06 を実行する。
- **許容誤差**: 完全一致。**自動化**: 自動。**合否**: 全ケースが期待どおり。

### 6.1 一致の基準(設計判断 VP-D2)
| 比較 | 基準 | 根拠 |

| 同じビルド・同じ実行環境での2回の実行 | **ビット同一** | エンジンは乱数(COM-11、固定アルゴリズム)以外に非決定の要素を持たない設計。時間を積分する状態は倍精度(COM-05)。同じ計算を同じ順で行えば同じビット列になる |

### VER-NF-003 決定性
- **目的**: 同じパッチ・同じ入力・同じサンプルレートなら出力が再現する。
- **区分**: 再現性。**対応要求**: REQ-NF-003。
- **前提環境**: TE-1。(d) は TE-1 と TE-4(ブラウザ内のオフライン描画)。
- **入力**: 再現性試験パッチ RP-1(18種を各1個以上含み、乱数を使うモジュール(MOD-NSE-001、MOD-RND-001)、フィードバック、MIDIイベント列、途中のパラメータ変更とグラフ変更を含む)。`fs` は 44100、48000、96000。長さは各10秒(設計判断。位相・タイマの累積誤差が表に出るには短い可能性があるため、48000 Hzでは10分の長時間版も1回実行する)。
- **手順と期待結果**:
  - **VER-NF-003a(2回一致)**: RP-1 を初期状態から2回描画する。期待: 全出力(デバイスへ渡す値と、全モジュールの出力ポート)がビット同一。プロセスを起動し直した2回でも同じ。
  - **VER-NF-003b(保存復元)**: 途中のステップ `k` で検証用スナップショット(data-contract §6。エンジンのコードを直接呼んで取得・適用する。製品のコマンドではない)を取り、別の個体に復元して続きを描画する。取らずに続けた場合と比較する。期待: モジュール単体(各仕様の `保存復元` 種別のTV。内部状態を持つ仕様に各1件)も、RP-1 のパッチ全体(ケーブルが運ぶ途中の値と出力段の状態を含む: DAT-14)も、**ビット同一**(COM-14、DAT-18)。`k` はブロックの途中を含む複数の位置で試す。スナップショットをJSONに書いて読み戻しても同じ(数値の表現 DAT-15、大きな配列 DAT-16、非有限値の表記)。`fs` が違うスナップショットは拒否される(DAT-17)。なお、利用者向けのパッチ保存(`patch.save`/`patch.load`)は内部状態を含まず、読込後は初期状態から始まる(VER-F-007c)。
  - **VER-NF-003c(ブロック長)**: RP-1 と VER-F-004a の全TVを、ブロック長1と128で実行する。期待: ビット同一。パラメータ変更・グラフ変更・MIDIイベントは、両方で同じサンプル番号に適用する。
  - **VER-NF-003d(環境間)**: RP-1 を、Node.js上のオフライン実行と、§10 の各候補環境のブラウザ内で描画する。期待: 差が、関係するモジュールのTVの許容誤差内。最大差を記録する。許容を超えた場合は、差が出たモジュールと関数を特定して記録し、不合格とする。
  - **VER-NF-003e(乱数)**: COM-11 の参照値(seed 0、1、12345 の初期状態と `next()`、`uniform()`)を実装が再現する。期待: 整数値は完全一致。
  - **VER-NF-003f(サンプルレート変更)**: `fs` を変えると全状態が再初期化される(COM-05、product-spec §5.3)。変更後の出力が、その `fs` で初期状態から始めた出力とビット同一。
- **測定方法**: 出力列のバイト列比較(ハッシュの比較でよい。不一致時は最初に食い違うサンプル番号とポートを報告)。
- **自動化**: 自動((d) のブラウザ内描画は半自動)。**合否**: (a)(b)(c)(e)(f) はビット同一、(d) は許容誤差内。

## 7. 性能(REQ-NF-004、REQ-NF-005)— 測定のみ。合否は出さない

**遅延・CPU負荷の数値目標は未決である(OPEN-001)。** この節は、測定方法と、目標を決める手順だけを定める。測定を実施しても「性能要件を満たした」とは扱わない。本節の測定区間・試行回数・パッチ規模は**設計判断(初期案 VP-D3)**で、最初の測定でばらつきを見て見直してよい(見直したら記録する)。

### 7.1 測定対象パッチ(BP)
測定パッチは、パッチJSONとしてリポジトリに置き、版を付ける。ポート名は各モジュール仕様 §3 のもの。

| ID | 内容 | 目的 |

| BP-0 | 空のパッチ(MOD-IO-001 のみ) | エンジンと出力保護だけの基礎負荷。遅延測定の基準 |
| BP-1 | 基本の1声: MOD-IO-002 `PITCH` → MOD-OSC-001 `pitch`、MOD-OSC-001 `saw` → MOD-FLT-001 `in`、MOD-FLT-001 `out` → MOD-AMP-001 `in1`、MOD-IO-002 `GATE` → MOD-ENV-001 `gate`、MOD-ENV-001 `env` → MOD-AMP-001 `cv1`、MOD-AMP-001 `out` → MOD-IO-001 `IN_L` | 典型的な使い方。遅延測定の対象 |
| BP-N | 連鎖(MOD-OSC-001 `saw` → MOD-FLT-001 `in`、MOD-FLT-001 `out` → MOD-AMP-001 `in1`、MOD-AMP-001 は `gain=1`)を `N` 本並べ、MOD-MIX-001 を多段にして束ね、MOD-IO-001 `IN_L` へ。各MOD-OSC-001 の `tune` は互いに変える。`N` = 1, 2, 4, 8, 16, 32, 64, …(倍々) | モジュール数に対する負荷の伸び。音切れが始まる規模の探索 |

| BP-POLY | BP-1 を16チャンネルで鳴らすパッチ | ポリフォニーの負荷。**OPEN-004 の解消後に定義・実行** |

### VER-NF-004 CPU負荷の測定
- **目的**: 音切れなく実時間処理できるモジュール数・負荷を測定し、目標を決める材料を得る。
- **区分**: 性能。**対応要求**: REQ-NF-004。
- **前提環境**: TE-4(§10 の各候補環境。実ブラウザ・実デバイス)。補助として TE-1(オフライン実行の処理速度)。
- **入力**: BP-0、BP-1、BP-N、BP-ALL、BP-M(BP-POLY は OPEN-004 後)。音が出続ける状態にする(MOD-OSC-001 は常時発振。BP-1 は試験用のMIDI列でノートを保持)。
- **指標**:
  | 指標 | 定義 | 取り方 |
  |---|---|---|
  | 負荷値 | 1ブロックの処理時間 ÷ 1ブロックの再生時間(128/`fs`)。1.0を超えるとアンダーラン(F-021-006、確度medium) | 試験用ビルドで、ブロックごとの処理時間を計測する。描画スレッド内で高精度の時計が使えるかは環境に依存するため、使える手段を環境別に記録する(EC-07)。使えない環境では、TE-1 の「処理時間 ÷ 描画した音声の時間」で代替し、代替であることを記録する |
  | 負荷値の分布 | 中央値、95パーセンタイル、99パーセンタイル、最大 | 測定区間の全ブロック |
  | 音切れ回数 | 測定区間で、処理が間に合わなかった回数 | 負荷値が1.0を超えたブロックの数。あわせて、エンジンが数える処理済みフレーム数と、AudioContextの時刻から求めたフレーム数の差を記録する。ブラウザがアンダーランの指標を提供する場合はそれも記録する |
  | 音切れが始まる規模 | BP-N で、音切れ回数が0でなくなる最小の `N` | `N` を倍々に上げ、境界の前後を2分して絞る |
  | メモリ | エンジンが確保するバッファの量(MOD-DLY-001 の遅延バッファ等) | 計算値と、ブラウザの計測手段があればその値 |
  | オフライン処理速度(補助) | TE-1 で、描画した音声の時間 ÷ 処理時間 | ブラウザの影響を除いたエンジン単体の速さ。実時間での音切れの有無を示すものではない |
- **手順**: (1) §3 の記録項目を残す。他のアプリケーションを閉じ、電源接続・省電力設定を記録する。(2) パッチを読み込み、音声を開始する。(3) 準備区間10秒は捨てる。(4) 測定区間60秒の全ブロックを記録する。(5) 同じ条件で5回繰り返す(毎回ページを読み込み直す)。(6) UIを表示して操作している状態と、UIを操作していない状態の両方で測る(メインスレッドの負荷が描画スレッドに及ぶかを見る)。(7) `fs` は、その環境の既定の出力デバイスのレートと、48000 Hz(DEC-107 の要求値。異なる場合)。
- **期待結果・許容誤差**: **なし(目標未決)**。機能としての期待は「測定が完了し、記録が揃う」ことだけ。
- **自動化**: 半自動(測定は自動。環境の準備と記録は人手)。
- **合否**: **判定しない。測定値を記録し、オーナーが目標を決定する(OPEN-001)。** 負荷値が1.0を超える構成が見つかった場合も、不合格ではなく測定結果として報告する。

### VER-NF-005 遅延の測定
- **目的**: 操作から音の変化までの遅延を測定し、目標を決める材料を得る。
- **区分**: 性能。**対応要求**: REQ-NF-005。
- **前提環境**: TE-4。内部区間は TE-3 でも測れる。
- **入力**: BP-1(と BP-0)。操作は次の4種: (i) UIでのパラメータ変更、(ii) エージェントの `param.set`(共通コマンドAPI)、(iii) 同じくMCP経由、(iv) MIDIノートオン。
- **測定区間(経路を分けて測る)**:
  | 区間 | 始点 → 終点 | 取り方 |
  |---|---|---|
  | L1 制御側 | 操作の発生(UIの入力イベント、サーバーの要求受信、MIDIメッセージの受信時刻)→ エンジンへのメッセージ送信 | 試験用ビルドの時刻記録 |
  | L2 エンジン適用 | メッセージ送信 → 変更が現れる最初の出力サンプル | エンジン内で、適用したブロックの先頭フレーム番号を記録。ブロック境界への量子化(最大128フレーム。product-spec §5.6)を含む |
  | L3 出力 | エンジンが書いたサンプル → スピーカー | 計算値: `baseLatency` + `outputLatency`(F-021-010。`outputLatency` は機材依存で動的に変わるため、測定区間の最小・最大を記録) |
  | L4 エージェント往復 | エージェントが要求を送信 → 応答を受信 | エージェントクライアント側の時計。(ii) と (iii) を別に測る |
  | L5 端から端(実測) | 操作の発生 → 音の変化(物理) | 出力をループバックまたはマイクで録音し、操作と同時に鳴らす基準信号(または操作信号を録音の別チャンネルへ入れたもの)との時間差を読む。機材(オーディオインターフェース、ケーブル)を記録する。機材がない環境では L5 は「未測定」とし、L1+L2+L3 を推定値として**推定であると明記**して記録する |
- **指標**: 各区間の中央値、95パーセンタイル、最大、最小。単位はミリ秒(L2 はフレーム数も)。
- **手順**: (1) §3 の記録項目を残す(特に出力デバイスの種類。Bluetooth等は別条件として分ける)。(2) BP-1 を読み込み音声を開始する。(3) 各操作を、ブロック周期と同期しない間隔(乱数seedを固定した不規則な間隔)で100回行う。(4) これを3回繰り返す。(5) 負荷のある状態(VER-NF-004 の BP-N で音切れが始まる規模の半分)でも同じ測定をする。(6) `latencyHint` は既定(`interactive`: F-021-009)。他の値を試す場合は別条件として記録する。(7) 要求したサンプルレートと出力デバイスのレートが異なる条件を1つ含め、再サンプリングによる差(F-021-008)を記録する。
- **期待結果・許容誤差**: **なし(目標未決)**。構成上の下限(product-spec §9: ブロック境界の量子化+`baseLatency`+`outputLatency`)と測定値の関係を報告に書く。
- **自動化**: L1〜L4 は半自動、L5 は手動。
- **合否**: **判定しない。測定値を記録し、オーナーが目標を決定する(OPEN-001)。**

### 7.4 目標を決める手順
1. VER-NF-004、VER-NF-005 を、§10 の主対象候補の環境で実施する(少なくとも、性能の異なる機材2台以上。機材の選定はオーナーと決める)。
2. 結果を、環境別・パッチ別の表(指標の中央値・95パーセンタイル・最大、試行間のばらつき)にまとめ、生データとともに提出する。構成上の下限と、測定方法の限界(L5 の機材、時計の精度)を併記する。
3. オーナーが、利用場面に照らして目標(例の形式: 「基準機材で、BP-N の `N` がいくつまで音切れ0」「操作から音までの遅延の95パーセンタイルがいくつ以下」)を決める。**目標値の案を本書の側から固定しない。**
4. 決定を plans/decisions.md に記録して OPEN-001 を閉じ、REQ-NF-004/005 と product-spec §9 を更新する。本書に、合否基準を持つ小項目(VER-NF-004b、VER-NF-005b)と基準機材の定義を追加する。
5. 目標を満たせない場合の分岐は DEC-102 のとおり(BP-M の結果から、負荷の大きいモジュールをWebAssembly化の候補にする)。対応後に再測定する。
6. 目標が決まるまで、性能の回帰は「前回の測定値との比較」として記録するだけにする(合否にしない)。

## 8. 音質(REQ-NF-007)— 測定のみ。合否は出さない

**音質の数値目標は未決である(OPEN-006)。** 機能再現(§4)とは別に扱う。ここでの測定値が悪くても、機能再現の不合格ではない。逆に、VER-F-004 に合格しても音質は未評価である。

### VER-NF-007 音質の測定
- **目的**: エイリアシング等の音質を測定する方法を定め、目標を決める材料を得る。
- **区分**: 音質。**対応要求**: REQ-NF-007。
- **前提環境**: TE-1(オフライン実行。`fs`=48000 を基本とし、44100 と 96000 でも測る)。
- **測定項目**: モジュールごとの測定方法(入力、窓、区間)は**各仕様の「音質要件」の記述が正本**で、本書は複製しない。
  | 小項目 | 対象 | 測定方法の正本 | 記録する指標 |
  |---|---|---|---|
  | VER-NF-007a | MOD-OSC-001 の折り返し成分 | MOD-OSC-001 §6「音質要件」 | 基本波に対する折り返し成分の比(dB)。周波数別・波形別 |
  | VER-NF-007b | MOD-LFO-001 の高周波設定時の折り返し成分 | MOD-LFO-001 §6「音質要件」 | 同上 |
  | VER-NF-007c | MOD-FLT-001 の自己発振時の折り返し成分と音程精度 | MOD-FLT-001 §10「音質要件」 | 折り返し成分の比(dB)、音程のずれ(cent) |
  | VER-NF-007d | MOD-AMP-001 のジッパーノイズと振幅変調時の歪み | MOD-AMP-001 §10「音質要件」 | ステップ後のスペクトルの広がり、折り返し成分のレベル |
  | VER-NF-007e | MOD-MIX-001 のクリップ歪み | MOD-MIX-001 §10「音質要件」 | 折り返し成分のレベル |
  | VER-NF-007f | MOD-DLY-001 の補間による高域損失、遅延時間変調 | MOD-DLY-001 §10「音質要件」 | 周波数応答の差、周波数の変動幅 |
  | VER-NF-007g | MOD-NSE-001 の白色性 | MOD-NSE-001 §6「音質要件」 | 帯域ごとの平均パワーの最大/最小比(dB) |
  | VER-NF-007h | 製品の出力段(product-spec §8.1)の歪みとクリック | 本書(下記) | 下記 |
  | VER-NF-007i | グラフ変更時のクリック(削除・切断時の抑制は初期版で行わない: product-spec §5.7) | 本書(下記) | 不連続の大きさ |
  | VER-NF-007j | 試聴 | 本書(下記) | 所見 |
- **VER-NF-007h の方法**: MOD-IO-001 `IN_L` に 1 kHz の正弦波を、デバイスへ渡す値で −20、−6、−1、0、+6 dBFS 相当になる振幅で入れる(MOD-IO-001: ±5 V = ±1.0)。出力(デバイスへ渡す値)を 2^16 サンプル取り、Hann窓のFFTで、基本波に対する高調波の合計(全高調波歪み)と折り返し成分を記録する。リミッターが働く前後の利得の変化(立ち上がりと復帰の時間波形)、フェードイン・緊急停止・ミュートの瞬間の不連続の大きさ(隣接サンプル差の最大)も記録する。**リミッターのしきい値・時定数、マスター音量の既定値・フェード時間は未決**(product-spec §8.1。初期案は確定値ではない)なので、候補の設定ごとに測り、決定の材料にする。

- **期待結果・許容誤差**: **なし(目標未決)**。
- **自動化**: (a)〜(i) 自動(測定と記録)、(j) 手動。
- **合否**: **判定しない。測定値を記録し、オーナーが目標を決定する(OPEN-006)。**

### 8.3 目標を決める手順
1. VER-NF-007 を実施し、モジュール別・条件別の表と、スペクトル図、試聴の所見を提出する。
2. オーナーが、どの項目に目標を置くか(例: オシレータの折り返し成分、出力段の歪み)と、その値を決める。改善策(バンドリミット化、オーバーサンプリング、パラメータの平滑化)は、モジュール仕様の改訂を伴う(MOD-OSC-001 §6: バンドリミット化は#3以降の選択)。**仕様を変えた場合、機能再現のTVも変わる**ので、VER-F-004c に従い再試験する。
3. 決定を plans/decisions.md に記録して OPEN-006 を閉じ、REQ-NF-007 を更新する。本書に合否基準を持つ小項目(VER-NF-007k 以降)を追加する。
4. リミッターのしきい値・時定数とマスター音量の既定値・フェード時間(product-spec §8.1)も、この測定と VER-S-001/003 の結果を材料に決める。決まった値は product-spec §8.1 に書き、VER-S-001b、VER-S-003b の期待値とする。

## 9. 安全性(REQ-S)

安全性の合否は、**不変条件(範囲を超えない、拒否される)が破れないこと**で決める。音質(リミッターの効き方の良し悪し)とは別である。設定値が未決の機構は、不変条件だけを合否にし、設定値との一致は「値の確定後」の小項目に分ける。

出力保護の順序(product-spec §8.1): MOD-IO-001 → 非有限値除去 → マスター音量 → リミッター → 最終クリップ → デバイス。以下「出力」は、**デバイスへ渡す直前の値**(最終クリップの後)を指す。

### VER-S-001 リミッターと出力範囲
- **目的**: デバイスへの出力が名目範囲[-1,1]を超えない。
- **区分**: 安全性。**対応要求**: REQ-S-001。
- **前提環境**: TE-1(出力保護を含むエンジン)。裏取りとして TE-4 で試験用ビルドの出力記録。
- **手順と期待結果**:
  - **VER-S-001a(不変条件)**: 次の入力のすべてで、全サンプルの出力が −1.0 以上 +1.0 以下で、有限値である。(i) MOD-IO-001 `IN_L`/`IN_R` に ±12 V の矩形波・直流・正弦波。(ii) MOD-IO-001 `level=2`(最大)。(iii) マスター音量を人の操作で最大にした状態。(iv) 0 V から ±12 V への1サンプルの跳躍(リミッターの立ち上がりより速い変化)。(v) 利得1以上のフィードバックループ(VER-F-011a)を出力へつないだもの。(vi) 乱数seedを固定して生成した多数のパッチ・パラメータ(無作為試験。件数とseedを記録)。(vii) `patch.load`、モジュール削除、サンプルレート変更の瞬間。
  - **VER-S-001b(常時有効)**: リミッターを無効にするコマンド・パラメータ・設定が、UIの通常操作にもエージェントの操作にも存在しない。リミッターが利得を下げている間、その事実が状態または通知で分かるか(提供する場合。契約の定義による)。
  - **VER-S-001c(最終クリップ)**: リミッターを試験用に外した構成でも、最終クリップにより出力が ±1.0 を超えない(保険が単独で働くこと)。
  - **VER-S-001d(設定値。値の確定後)**: しきい値・時定数は**未決**(product-spec §8.1、OPEN-006 と併せて決定)。確定後に、定常の正弦波入力に対する出力レベルと、立ち上がり・復帰の時間が、確定値と一致することを確かめる。**確定するまで「未実行」。**
- **許容誤差**: (a)(c) は許容なし(`|out| ≤ 1.0` を厳密に。1サンプルでも超えたら不合格)。
- **測定方法**: 出力列の最大絶対値と非有限値の個数。
- **自動化**: 自動。**合否**: (a)(b)(c) が成立。

### VER-S-002 緊急停止
- **目的**: 緊急停止をUIとエージェントの両方から即時に実行でき、出力が無音になる。
- **区分**: 安全性。**対応要求**: REQ-S-002。
- **前提環境**: TE-1+TE-2(時刻と値)、TE-3(UIとエージェントの両経路)。
- **入力**: `engine.panic`、UIの緊急停止ボタン。過大な音を出し続けるパッチ(VER-S-001a の (v))。
- **手順と期待結果**:
  - **VER-S-002a(無音)**: 実行後、エンジンが要求を受け取った**次のブロックの先頭以降**、出力の全サンプルが厳密に 0 である。「即時」の測定可能な定義は「エンジン到達後、次のブロック先頭まで」とする(設計判断 VP-D4。product-spec §5.6 の反映時刻と同じ。要求の発生からエンジン到達までの時間は VER-NF-005 の L1 と同じ方法で測り、記録する。この時間に目標値を置くかは OPEN-001 と併せてオーナーが決める)。
  - **VER-S-002b(状態の初期化)**: 全モジュールの内部状態が `reset()` 後の初期状態(COM-10)になる。パッチ(構成・パラメータ)・リビジョン・履歴は変わらない(CMD-23)。通知 EVT-03 が出る。
  - **VER-S-002c(両経路)**: UIのボタンと `engine.panic`(共通コマンドAPI、MCP)のどれからでも (a)(b) が成立する。
  - **VER-S-002d(解除は人だけ)**: エージェントの `engine.release_panic` は ERR-005(AX-10a)。エージェントからのどの要求でも、停止が解除されず、無音が続く(`output.set_level`、`param.set`、`patch.load`、`patch.new`、`history.undo`、`batch`、再度の `engine.panic` を含む)。人のUI操作(`engine.release_panic`)で解除でき、解除後はフェードインから始まる(VER-S-003)。MCPに解除のツールがない。
  - **VER-S-002e(状況を問わない)**: 音声が `stopped` のとき、負荷が高いとき(VER-NF-004 の音切れが始まる規模)、`batch` の適用中、他のクライアントが大量に要求を送っている最中でも実行できる。
  - **VER-S-002f(再送・競合)**: 緊急停止の再送・重複が害を起こさない(2回実行しても成功し、無音のまま)。古い `expected_revision` を付けても拒否されない(CMD-23: 止める操作を競合で失敗させない)。
- **許容誤差**: (a) は厳密に 0。
- **自動化**: 自動(UIボタンは自動操作)。実機での聴感確認(TE-4)は手動で1回。
- **合否**: 全ケースが成立。

### VER-S-003 起動時・読込時の低音量とフェードイン
- **目的**: 起動時・パッチ読込時・音声開始時の出力音量が低い値から始まり、フェードインする。
- **区分**: 安全性。**対応要求**: REQ-S-003。
- **前提環境**: TE-1(マスター音量段の挙動)、TE-3(契機の網羅)。
- **入力**: 常に最大振幅を出すパッチ(MOD-IO-001 に ±5 V 以上の直流または正弦波)。契機: (i) 最初の「音声開始」、(ii) `patch.load` と自動保存からの復元、(iii) 中断からの再開(`suspended` → `running`)、(iv) 緊急停止の解除。
- **手順と期待結果**:
  - **VER-S-003a(不変条件)**: 各契機の直後、マスター音量の利得が (1) 0 または十分小さい値から始まり、(2) 単調に増え、(3) 目標値(低い既定値)を超えない。契機の直後の最初のブロックに、フェード前の利得のサンプルが1つも出ない。前回の音量設定が高くても、契機の後は低い既定値から始まる(「パッチ読込時」に前回の音量へ戻さない)。エンジン内のモジュール状態が初期状態から始まる(復元直後に、前の音の残りが出ない)。
  - **VER-S-003b(設定値。値の確定後)**: 既定値とフェード時間は**未決**(product-spec §8.1。初期案 −20 dB・50 ms は根拠未測定のため確定値ではない)。確定後に、測定した利得の時間変化が確定値と一致することを確かめる。**確定するまで「未実行」。** それまでは、測定した開始値・到達値・到達時間を記録する。
  - **VER-S-003c**: エージェントが契機を作れる場合(`patch.load`)も同じ。エージェントがフェードを省略・短縮する手段がない。
- **許容誤差**: (a) は順序関係の成立(厳密)。(b) は確定時に定める。
- **測定方法**: 入力が一定のときの出力の包絡(出力 ÷ 入力)。
- **自動化**: 自動。**合否**: (a)(c) が成立。

### VER-S-004 エージェントの音量上限
- **目的**: エージェントが設定できる出力音量に上限があり、上限の変更は人のUI操作に限られる。
- **区分**: 安全性。**対応要求**: REQ-S-004。
- **前提環境**: TE-2、TE-3。
- **入力**: `output.set_level`(エージェントから、UIから)。
- **手順と期待結果**:
  - **VER-S-004a**: エージェントが、上限以下・上限ちょうど・上限超過・極端な値(非常に大きい値、NaN、∞、負)を要求する。期待: 上限(`agent_max_level_db`)以下は適用。上限超過は ERR-302 で**拒否**され(上限へクランプされない。AX-10b)、範囲外は ERR-123、数値でない値は ERR-003。**適用後のマスター音量が上限を超えない**。応答から、現在の音量と上限が分かる。
  - **VER-S-004b**: エージェントから上限そのものを変える手段がない(コマンド、`batch` 内、`patch.load` で読み込むパッチの内容、MCPのどれでも)。パッチには音量・上限の項目がなく(DAT-01)、それに当たるキーを足したパッチは未知のキーとして拒否される(DAT-V05)。読込で上限が広がらず、マスター音量が上限を超えない。
  - **VER-S-004c**: 人がUIで上限を変えると、以後のエージェントの要求は新しい上限で判定される。人が音量を設定すると上限も同じ値になる(CMD-25)。起動時・パッチ読込時・音声開始時に音量が既定値へ戻ると、上限も既定値に戻る(エージェントが `patch.load` で上限を広げられないこと、逆に読込で音量が上がらないこと)。音量と上限は取り消し・やり直しの対象外で、`history.undo` で変わらない(operation-contract §2.1)。
  - **VER-S-004d**: 要求の発信元(人かエージェントか)の判定を、エージェントが偽れない(要求の中の自己申告で人として扱われない。判定は接続の種別で行う。VER-S-007c)。
  - **VER-S-004e**: MOD-IO-001 の `level`・`mute` はパッチのパラメータで、エージェントが `param.set` で変えられる(範囲 0〜2)。これを最大にしても、後段のマスター音量とリミッターにより VER-S-001a が成立する。
- **注記**: 上限の定義は初期案(「人が設定した現在値まで」: product-spec §8.1、CMD-25)。音量の範囲(−60〜0 dB)と既定値は暫定・未決である。本項目は「上限を超えない」「上限を変えられない」という不変条件を合否にし、具体値には依存しない(試験は契約の現在値を読んで使う)。
- **許容誤差**: 適用後の値 ≤ 上限(厳密)。
- **自動化**: 自動。**合否**: 全ケースが成立。

### VER-S-005 待受と認証
- **目的**: 外部操作の待受が127.0.0.1に限られ、接続にトークンが要る。
- **区分**: 安全性。**対応要求**: REQ-S-005。
- **前提環境**: TE-3。(a) は、同じネットワークに別のホストを1台置く(置けない場合は、試験機の127.0.0.1以外の自アドレスへの接続で代える。その場合は代替と記録)。
- **手順と期待結果**:
  - **VER-S-005a(待受)**: サーバー起動後、OSの手段で待受ソケットを列挙する。期待: 待受アドレスが 127.0.0.1 だけ(全アドレス待受 `0.0.0.0`・`::` がない)。試験機のLAN側アドレスと別ホストからの接続が、HTTP・WebSocketとも確立しない。MCPアダプタがネットワークの待受を持つ方式(OPEN-008 がローカルHTTPに決まった場合)は、それも同じ条件。起動オプションや環境変数で待受を広げられない(広げる手段がある場合は、既定で無効であり、製品仕様に記載があること)。
  - **VER-S-005b(トークン)**: トークンなし、誤ったトークン、形の壊れたトークン、前回起動時のトークンで、全コマンド(読出しを含む)とWebSocket接続を試す。期待: すべて ERR-004 で拒否(AX-10e)。状態は不変で、応答にパッチの内容が含まれない。正しいトークンでは成功する。トークンは起動ごとに変わり、推測できない長さ・乱数源である(生成方法を確認)。トークンがログ・通知・`patch.get`・保存ファイルに出ない。
  - **VER-S-005c(ブラウザからの不正要求)**: 別のオリジンのページから、127.0.0.1 の待受へHTTP・WebSocketの要求を送る(Originが自サーバーと異なる要求)。期待: 拒否(product-spec §8.2)。誤ったOriginは ERR-004。Originヘッダを持たない要求(ブラウザ以外のクライアント)は、トークンで判定される(詳細は OPEN-007 の確定に従う)。
  - **VER-S-005d(認証の試行)**: 誤ったトークンを多数回送っても、サーバーが停止せず、正しいトークンの接続に影響しない。
- **注記**: 認証方式の詳細は OPEN-007(初期案: 起動時トークン)。方式が変わった場合、(b) を新方式に合わせて改訂する。不変条件(認証なしでは何もできない)は変わらない。
- **自動化**: 自動((a) の別ホストは半自動)。**合否**: 全ケースが成立。

### VER-S-006 非有限値(NaN/∞)
- **目的**: 非有限値が出力に出ず、発生を検出して通知できる。
- **区分**: 安全性。**対応要求**: REQ-S-006。
- **前提環境**: TE-1、TE-2(通知)。
- **手順と期待結果**:
  - **VER-S-006a(モジュール単位)**: 各モジュール仕様の `無効入力` 種別のTVのうち、NaN/∞を扱うもの(VER-F-004a の一部)。期待: 入力のNaN/∞は 0 V 扱い、出力のNaN/∞は 0、パラメータのNaN/∞は既定値(COM-12)。
  - **VER-S-006b(出力段)**: 試験用の注入口で、MOD-IO-001 の後・非有限値除去の前に NaN、+∞、−∞ を、単発・連続・通常値との混在で入れる。期待: デバイスへ渡す値に非有限値が1つもない(0に置換)。発生回数の計数が注入した個数と一致する。置換後もリミッターの内部状態が壊れず、注入をやめた後の出力が、注入しなかった場合の値へ戻る(リミッターの状態が非有限値で汚れない)。
  - **VER-S-006c(通知)**: 発生が EVT-04 でUIとエージェントに通知され、`engine.get_status` の `output.nonfinite_count` が増える(大量発生時は間引かれ、累計が載る。通知が洪水にならないこと)。MOD-IO-003 の `nonfinite_count` は、その入力のNaN/∞の個数と一致する(MOD-IO-003 のTV)。
  - **VER-S-006d(無作為試験)**: VER-S-001a (vi) の無作為パッチで、全モジュールの全出力ポートに非有限値が現れない。
  - **VER-S-006e(コマンド経由)**: `param.set` 等で NaN/∞ を送る(JSONで表せる形と、表せない形の両方)。期待: 文字列や `null` での代用は ERR-122、JSONとして不正な表記は ERR-001 で拒否され(operation-contract §12.1)、パッチグラフに非有限値が入らない。`patch.load` のパッチ内の非有限値も拒否される。
- **許容誤差**: 非有限値の個数は厳密に0。計数は完全一致。
- **自動化**: 自動。**合否**: 全ケースが成立。

### VER-S-007 エージェントの権限の境界
- **目的**: エージェントの操作がパッチと音量の範囲に限られ、任意パスのファイル操作・任意ホストへの送信・プロセス終了ができない。
- **区分**: 安全性。**対応要求**: REQ-S-007。
- **前提環境**: TE-3。サーバーのファイル操作とネットワーク通信を外から監視する(OSの手段、または試験用の監視)。
- **手順と期待結果**:
  - **VER-S-007a(コマンドの全数検査)**: operation-contract の全コマンドとMCPの全ツールを列挙し、それぞれが product-spec §8.2 の「エージェントの権限」に収まることを確かめる。期待: エージェントが実行できるコマンドは、operation-contract §6 の表で権限が「両方」のものだけ。任意パスの読み書き、任意ホストへの送信、サーバー停止、コード評価に当たるコマンドが存在しない(送ると ERR-002)。人のみのコマンド(`engine.start`、`engine.release_panic`、`patch.delete`)は ERR-005(operation-contract §15.2)。
  - **VER-S-007b(保存名とパス)**: `patch.save`/`patch.load` の名前に、上位参照(`..`)、パス区切り(`/`、`\`)、絶対パス、ドライブ名、空文字、極端に長い名前、制御文字、ヌル文字、OSの予約名、URL、符号化した区切り文字(`%2e%2e%2f` 等)、専用フォルダの外を指すシンボリックリンクを指定する。期待: すべて ERR-201 で拒否(AX-10c)。`patch.read`・`patch.delete` の名前でも同じ。**専用フォルダの外に、ファイルの作成・変更・読出しが1件も起きない**(監視で確認)。名前の規則(DAT-31: 英小文字・数字・`_`・`-`、1〜64文字)の境界(64文字と65文字、大文字、非ASCII、先頭の記号)も試す。専用フォルダ内の正しい名前では成功する。専用フォルダ内に、外を指すシンボリックリンクを試験側で置いても、たどられない。フォルダ内のファイル数の上限(暫定1000件)で ERR-106。大きすぎるパッチは ERR-206。エージェントは、人が保存したファイルと読めないファイルを `overwrite: true` でも上書きできず(ERR-005)、自分が最後に保存したファイルは上書きできる(operation-contract §15.3)。エージェントは保存パッチを削除できない(ERR-005)。保存の途中で失敗しても、既存のファイルが壊れない(一時ファイルに書いてから置き換える: CMD-12)。
  - **VER-S-007c(発信元の区別)**: 人のUI操作に限られる操作(緊急停止の解除、音量上限の変更、音声開始)を、エージェントの接続から、UIが送るのと同じ形の要求で送る。期待: ERR-005 で拒否。操作者は受け口が決め、要求に `actor` や `client_id` で「人である」と書いても通らない(operation-contract §3.1)。応答の `actor.kind` が `agent` である。
  - **VER-S-007d(音声の自動開始)**: エージェントの `engine.start` は ERR-005。エージェントのどの要求でも、音声状態が `stopped` → `running` にならない(VER-A-008c)。
  - **VER-S-007e(外部通信)**: 全試験の実行中、サーバーとブラウザのタブから 127.0.0.1 以外への通信が0件(テレメトリ・外部サービス連携なし: product-spec §8.2)。パッチやコマンドにURLを入れても取得されない。VER-NF-001 のネットワーク遮断下の試験と併せて確認する。
  - **VER-S-007f(コード評価)**: パッチ・コマンドの文字列項目(名前、メモ等。契約にある場合)に、スクリプト片・HTML・テンプレート記法を入れる。期待: 文字列として保存・表示されるだけで、UIでもサーバーでも実行されない。パッチの最上位などに未知のキー(例: `script`)を足したものは拒否される(DX-12)。`ui` 内の未知のキーは保持されるが、解釈も実行もされず、音に影響しない(DAT-10、DAT-11)。
  - **VER-S-007g(プロセス)**: サーバーを停止・再起動するコマンドがない。壊れた要求・巨大な要求・大量の要求でサーバーが異常終了しない(終了した場合は不合格)。
  - **VER-S-007h(資源)**: モジュール数・ケーブル数・`batch` の操作数・要求の大きさ・パッチの大きさの上限(operation-contract §16)が働く(ERR-106、ERR-011、ERR-206)。上限値は暫定で、性能の保証値ではない。上限いっぱいのパッチでタブが応答し続けるかは VER-NF-004 で測定して記録し、上限値の見直しの材料にする(応答性の合否は出さない)。
  - **VER-S-007i**: 受入例 AX-10a〜e を実行する。
- **許容誤差**: なし(範囲外の動作が1件でもあれば不合格)。
- **自動化**: 自動((a) の権限との照合は人が確認した対応表を正とし、コマンド一覧の変更を自動で検出する)。
- **合否**: (a)〜(i) が成立(上限が働くこと。上限値の妥当性は合否にしない)。

### VER-NF-006 版互換(旧版パッチの読込)
- **目的**: 保存データが版番号を持ち、旧版のパッチを読み込める。
- **区分**: 機能再現 / 異常系。**対応要求**: REQ-NF-006。
- **前提環境**: TE-2。
- **入力**: リポジトリに置く「版ごとの見本パッチ」(パッチ形式の版が上がるたびに、その版で保存した見本と、読込後に期待される `patch.get` を追加して固定する)。
- **手順と期待結果**:
  - **VER-NF-006a**: 保存したパッチに、パッチ形式の版(`schema_version`)と、各モジュールの種別(`type`)・仕様版(`spec_version`)がある(COM-14、data-contract §9.1)。
  - **VER-NF-006b**: 過去の全版の見本を現行版で読み込む。期待: データ契約 §9 の移行規則(および各モジュール仕様 §9 の移行規則)どおりの構成・パラメータになり、見本ごとの期待パッチと DAT-04 の意味で一致する(DAT-51、DAT-61)。応答の `migrated` と警告に移行の内容が入る。元のファイルは書き換えられず(DAT-60)、読込後に保存すると現行版になる。移行は古い版から順に1段ずつ適用される(DAT-55、DAT-56)。
  - **VER-NF-006c(異常系)**: 現行より新しい `schema_version`(DX-02)・`spec_version`(DX-11)、別の `format`(DX-03)は ERR-205。版番号の欠落・不正は ERR-204。期待: 拒否し、現在のパッチは不変(product-spec SC-H3、DAT-52)。移行後の検証に通らない旧版も全体が拒否される(DAT-58)。
  - **VER-NF-006d**: モジュール仕様の版だけが上がった場合(例: OPEN-003 による MOD-CLK-001 の改訂、OPEN-009 の見直し)に、旧仕様版で保存したパッチの扱いが、その仕様の §9 とデータ契約 §9.5 どおり。保存データに影響しない改訂にも「何もしない移行」が登録されている(DAT-56)。
  - **VER-NF-006e(移行関数の性質)**: 移行関数が純粋である(同じ入力に同じ出力。入力を書き換えない。時刻・乱数・ファイル・通信に依らない: DAT-57)。同じ見本を2回移行して結果が一致する。
  - **VER-NF-006f(仕組みの確認)**: 版が1つしかない間は、**試験専用の仮の旧版**と移行関数を用意して、移行の仕組み(順次適用、省略パラメータの補完の順 DAT-59、報告、失敗時の全体拒否)を確かめる(DAT-61)。
- **注記**: 初期版の公開時点では、版は1つだけで、実在する旧版からの移行は発生しない。その時点で実行できるのは (a)(c)(e)(f) と、版1の見本の往復である。(b)(d) は、**2つ目の版ができた時点から実行する**。初期版で (b)(d) を「合格」と扱わない(対象なし)。(f) の合格は、実在する旧版の移行の正しさを示さない。
- **許容誤差**: 完全一致。**自動化**: 自動。**合否**: 実行できる小項目が期待どおり。

### VER-NF-008 ライセンスと流用の確認
- **目的**: 第三者のコード・アセット・商標・外観を流用していない。採用ライブラリのライセンスが記録されている。

## 13. 本書の設計判断と未決事項

### 13.1 本書が置いた設計判断(見直し可)
| ID | 判断 | 理由 | オーナー確認 |
|---|---|---|---|
| VP-D1 | 機能再現・再現性・音質は、エンジンのコードを音声デバイスなしで直接実行して検証する。そのため、エンジンの処理部はブラウザ固有のAPIから切り離し、AudioWorklet内とオフライン実行で同じソースを使うことを実装に求める | product-spec §5.5 が「同じエンジンコードの直接実行」を認めている。実デバイスを通すと、値の比較も繰り返し実行もできない | 不要(実装計画への要求として伝える) |
| VP-D2 | 再現性の基準: 同一環境の2回・スナップショットからの復元・ブロック長1と128は**ビット同一**。異なる実行環境の間は**各TVの許容誤差内** | COM-14(ビット同一)、COM-05(1サンプル処理と一致)。環境間は数学関数の実装差がありうるため、COM-12/15 の許容誤差で扱う | **望ましい**(環境間でもビット同一を求めるなら、数学関数を自前実装にする必要があり、設計に影響する) |
| VP-D3 | 性能測定の初期案: 準備10秒、測定60秒、5試行(負荷)。操作100回×3試行(遅延)。BP-N は倍々で探索 | 目標値ではなく測定の手間と安定性の見積り。根拠となる実測はまだない。最初の測定でばらつきを見て見直す | 不要(測定結果とともに報告) |
| VP-D4 | 緊急停止の「即時」を「エンジン到達後、次のブロック先頭から厳密に無音」と定義する | product-spec §5.6 の反映時刻と同じ単位で、値で判定できる。要求の発生からエンジン到達までの時間は測定して記録するにとどめる | **望ましい**(到達までの時間に上限を置くかは OPEN-001 と併せて判断) |
| VP-D5 | 設定値が未決の安全機構(リミッター、起動時音量、エージェント上限)は、不変条件だけを合否にし、設定値との一致は値の確定後の小項目に分ける | 未決の値を満たしたと扱わないため。安全の最低線(範囲を超えない)は値によらず検証できる | 不要 |
| VP-D6 | VER-NF-008(ライセンス)は区分表の8区分に当てはまらないため「文書検査」として扱う | 性質が他と異なる | 不要 |
| VP-D7 | 候補環境に Edge(ENV-04)を加え、Firefox はOSごとに記録する1列にまとめた | Chromium系の別製品での差を見るため。Firefox/Safari は判断材料の収集が目的 | **望ましい**(試験する環境の数は手間に直結する) |
