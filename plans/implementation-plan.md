## 1. 読み方と規則

### 1.1 タスクの項目
各タスクは、目的・成果物・依存タスク・参照仕様・検証方法・状態・規模・入口(着手前に読む文書)を持つ。段階ごとの表で、同じ段階に共通する項目(入口など)は表の前にまとめて書く。

- **状態**は未決事項(OPEN)との関係だけを表す。
  - **着手可**: 未決事項に妨げられない。依存タスクが終われば始められる。
  - **保留(OPEN-…)**: その未決事項が解決するまで始めない(または完了にしない)。部分的に保留の場合は範囲を書く。
- **規模**は相対値(S / M / L)で、根拠を一言添える。日数・工数の数字は根拠がないため書かない。
- **依存**の列は、そのタスクを始める前に終わっている必要があるタスクである。タスクの一部だけが別のタスクを待つ場合は「**部分依存:**」の後に、待つ範囲とともに書く(その範囲以外は先に進められる)。
- 依存先(間接を含む)が一部保留のとき、依存元もその範囲に限って未完了とする(完了の報告にその範囲を「未実行」と書く)。該当するタスクは §5 に挙げる。
- **担当がオーナー**のタスク(決定タスク)は「担当: オーナー」と書く。それ以外は実装担当。

### 1.2 未決値の扱い
性能目標(OPEN-001)、音質目標(OPEN-006)、出力保護の定数(OPEN-010: マスター音量の既定値・フェード時間・リミッターのしきい値と時定数と方式。製品仕様 §8.1 が「初期案・未測定」とするもの)は、**「測定タスク → オーナー決定タスク」**の順に進める。出力保護の定数(TASK-1008 → TASK-1018)と音質目標(TASK-1007 → TASK-1009)は別々に決める。
- 決定前の実装は、値を**差し替え可能な設定値**として持ち、製品仕様 §8.1 の初期案を**仮値**として入れる。仮値を確定値として文書・試験に書かない。
- 決定前は、該当の検証(VER-NF-004 / VER-NF-005 / VER-NF-007、および出力保護の定数に依存する判定)を「目標を満たした」と報告しない。測定値の記録までを完了条件とする。

### 1.3 技術選定の範囲
決定済みは DEC-101〜DEC-112 の範囲(Web Audio API + AudioWorklet、TypeScript、Node.js 単一プロセス・127.0.0.1、タブ内エンジン、制御側の単一パッチグラフ、JSON保存、実サンプルレート、128フレーム、自作コード、出力保護の位置、音量を自動で上げない、非有限値の検出)。これを超える選定(ビルドツール、テストランナー、UIの描画方式、HTTP/WebSocketの実装、MCPのSDK、ブラウザ内保存の媒体、Node.js の対応版)は**固定せず、選定タスク**にする。選定タスクの成果物は、候補・選定理由・ライセンスの記録(decisions.md への `DEC-…` 追記と TASK-005 の一覧)である。

## 8. 本書で置いた設計判断
調査事実(`F-…`)ではなく、計画上の判断として置いたもの。仕様に関わるものは、該当タスクの成果物として正本側に記録する。
1. エンジン核と制御側を、ブラウザに依存しない純粋なコードとして先に作り、Node.js 上で検証例を回す(製品仕様 §5.5 の「同じエンジンコードの直接実行」に基づく進め方。検証計画 §2 の TE-1・TE-2 の成立条件と同じ)。
2. ポート・パラメータの定義を1か所に持ち、実装と `module.list_types` で共有する(TASK-006)。仕様の表との一致を検査する。
3. 出力保護の定数(OPEN-010)と性能・音質の目標(OPEN-001、OPEN-006)は、仮値のまま実装し、測定の後にオーナーが決める(§1.2)。決定タスクは別々にした(TASK-1018、TASK-1006、TASK-1009)。
4. MOD-CLK-001 は `run` 停止時の挙動だけを後回しにして、他を先に実装する(OPEN-003)。
5. ポートに `channels` を持たせる構造だけを先に入れ、ポリの動作は検証例ができてから実装する(OPEN-004)。
6. 画面からのノート入力(TASK-709)を UI のタスクに含め、Web MIDI と同じ経路でエンジンへ渡す(製品仕様 §2 SC-H2 の「画面操作でノート」)。操作契約にこの入力のコマンドはないため、コマンド・リビジョン・履歴の対象にしない。これは OPEN-012 の初期案であり、TASK-1019 でオーナーが確認する(エージェントからのノート送信を初期版に含めない判断: 操作契約 §6.1 と併せて)。
7. 既定の待受ポートを固定し、番号と保存フォルダの既定の場所は TASK-502 で決める(データ契約 §7.1・§14 からの引継ぎ)。本書では番号を固定しない。
8. 統合試験・測定の道具を1つのタスク(TASK-1017)にまとめ、受入・測定タスクの前提にする。
9. 仕様や契約にあるが担当タスクが読み取りにくかった作業を、次のとおり割り当てた: タブ側の起動・サーバー接続・単一タブ判定 = TASK-507、`engine_revision` の報告 = TASK-402(返値への反映は TASK-403・TASK-408)、ERR-011 = TASK-505、EVT-06 = TASK-803(配信は TASK-505)、利用者向けの起動・接続手順書 = TASK-604、Node.js の対応版 = TASK-002、既定ポートと保存フォルダの既定の場所 = TASK-502。
10. 初期案で進めている未決事項(OPEN-003、OPEN-011〜014)のオーナー確認を1つのタスク(TASK-1019)にまとめた。項目ごとに別々に確認してよい。
11. 受入・測定タスク(M10)の依存は、検証計画の各項目の前提環境と手順から拾った(例: VER-NF-001 はサーバー起動・音声開始・保存・MCP を通るため、TASK-1012 は M4・M6・M8 と TASK-706 に依存する)。
